- 目标岗位：AI 应用开发、AI 全栈、Python 后端（AI 方向）
- 读取前置：`docs/superpowers/specs/2026-04-18-docpilot-design.md`、`docs/product/mvp-scope.md`、`docs/architecture/assistant-harness-runtime.md`

## 1. 目的

本版本不追求把 BidPilot 做成泛化 Agent 平台，也不把尚未验证的
“多 Agent”“知识图谱”“生产级”当作卖点。目标是交付一个可重复演示、
可测试、可解释的投标文档智能执行产品闭环，并用它证明以下能力：

1. 能把真实业务状态建模在 PostgreSQL，而不是藏在 Prompt 或 Agent state 中。
2. 能把文档解析、混合检索、引用、生成、人工审核和导出串成可靠产品流程。
3. 能区分交互式 Harness 与长运行 LangGraph 工作流，并给出清晰边界。
4. 能对工具权限、审批、重试、幂等、成本、租户隔离和模型错误做工程治理。
5. 能用固定案例、运行 Trace 和质量报告证明系统不是一次性演示。

## 2. 发布定义

### 用户承诺

投标经理上传一份脱敏 RFP/方案资料包后，可以在一个项目中看到：

1. 已解析的资料与提取出的需求；
2. 某个章节使用了哪些证据、为何缺少证据；
3. Agent 如何规划并调用平台能力；
4. 何时需要人工批准，批准后如何继续；
5. 起草、审核、拒绝重跑、批准和导出的完整审计轨迹。

### 面试演示叙事

```text
创建投标项目
  -> 上传固定脱敏资料包
  -> 等待解析与索引完成
  -> 查看需求和检索证据
  -> 让 BidPilot Assistant 规划并启动一个章节起草
  -> 人工审核/拒绝或批准
  -> 导出批准版本
  -> 回看 Run、引用、审批、重试和成本记录
```

该叙事必须能在一份固定 demo 数据集上重复执行，不能依赖临时手工改库、
前端假数据或某一个未记录的模型返回。

## 3. 运行时边界

### 3.1 交互式 Assistant：StreamingHarness

面向浏览器对话的 Assistant 使用 `StreamingHarness`，负责：

- 模型一轮一轮地决定工具调用；
- 填补缺失参数、展示计划和工具进度；
- 强制经过 capability、RBAC、审计、额度和审批管线；
- 使用 `RuntimeRun`、`RuntimeEvent`、`RuntimeApproval` 持久化每个用户可见动作；
- 在需要长时间执行时，创建链接的工作流 Run，而不是在 HTTP 请求中硬跑。

它不是本地 Coding Agent，不执行 shell、任意网络、服务器命令或用户本地文件。
本产品是 Web SaaS，不能因为 Pi 的本地 Harness 范式而把 Pi SDK 引入服务端主路径。

### 3.2 长运行投标流程：LangGraph + Worker

LangGraph 只用于 Worker 内部的有状态流程，例如：

```text
解析 RFP -> 加载授权记忆 -> 检索证据 -> 规划 -> 起草
-> 质量审查 -> 人工审批 -> 写入版本/审计 -> 提议项目记忆
```

Celery/Redis 负责投递和异步执行；PostgreSQL 中的项目、章节、审核、审批、
ExecutionRun 和审计记录才是业务真相。LangGraph checkpoint 不能成为唯一状态源。

### 3.3 知识与记忆

| 消费者 | 真相来源 | 检索方式 | 当前边界 |
| --- | --- | --- | --- |
| 人类审核者 | 项目资料、章节、审核记录 | 页面和 API | 可编辑、可审计 |
| RAG | KnowledgeChunk + Evidence | 关键词 + 向量混合检索 + 重排 | 必须返回来源定位 |
| Assistant/Workflow | 已授权的 MemoryRecord | 有预算的 context pack | 只注入有证据、可见且未过期内容 |

知识图谱当前只允许“带证据的提案和逐项人工审核”。没有经过基准验证前，
不得把图谱投影为事实库，不做 3D 图谱展示，也不宣传“自动用户画像”。

## 4. 范围

### 必须完成

1. 一个稳定的投标资料到批准导出闭环。
2. Assistant 的多轮工具执行、缺参暂停、审批恢复、取消、幂等重放和后台工作流桥接。
3. 证据检索、章节引用、缺失证据标记，以及审核重跑。
4. 记忆的受控提案、审核激活、授权召回和工作流注入。
5. 固定 demo 数据集和离线评测报告。
6. 一次可重复部署、迁移、健康检查、备份恢复演练。
7. 面试需要的架构图、README、演示脚本和真实限制说明。

### 明确冻结

- 泛化工作流搭建器；
- 自治 Agent 团队、自组织通信和无限工具循环；
- 新的 RAG/图数据库/向量数据库迁移；
- WeKnora 集成、图谱可视化、A2A、微调、vLLM 和本地推理服务；
- 为“企业级”名义新增的微服务、Kubernetes、复杂计费和营销功能；
- 非阻塞核心闭环的前端视觉重构。

这些不是永远不做，而是不能抢占面试交付版本的验收资源。

## 5. 当前基线与诚实表述

当前仓库已有 Harness、LangGraph workflow、混合检索、MCP、受治理记忆、
评测契约和 CI 骨架。它们只有在下面的验收通过后才可被称为“已交付”。

在此之前：

- 不宣称已经有自动语义 Context Compaction；当前只存在预算截断和有界 context pack。
- 不宣称已有通用自治多 Agent；当前是受控 Workflow 节点和少量 campaign 编排。
- 不宣称图谱是生产事实库；当前是审核中的 graph proposal。
- 不宣称已具备生产可用性；必须完成真实端到端、质量门禁和恢复演练。

## 6. 功能需求与验收

### G1：源码和运行时稳定化

**目标**：形成一个可迁移、可测试、可部署的基线，消除当前工作区和公网行为不一致。

验收：

- [ ] 当前运行时修改、迁移和文档形成一个明确提交；`alembic upgrade head` 可执行。
- [ ] API/Worker Ruff 全绿；类型检查不再使用 `|| true` 作为发布门禁。
- [ ] API、Worker、前端测试在专用 `_test` 数据库中通过。
- [ ] 所有依赖服务都可由 Compose 启动，`web`、`api`、`worker`、`postgres`、`redis`、`minio` 健康。
- [ ] 公网部署前后版本、迁移 revision、健康检查和回滚点可记录。
- [ ] Provider 配置只在服务端解析；错误消息不暴露 API key、端点内部细节或上游原始响应。

### G2：黄金业务闭环

**目标**：一份固定资料包能完成完整投标章节工作流。

验收：

- [ ] 新建项目和上传资料包后，所有源文档有明确的 parse/index 状态。
- [ ] 系统能提取并展示至少一组可人工修正的 RequirementItem。
- [ ] 检索结果携带源文档、页码/片段/标题等 locator；检索失败显式降级，不能伪造引用。
- [ ] 至少一个章节能产出版本化 Markdown，且包含 evidence links 或明确 missing-evidence 标记。
- [ ] 审核者可评论、拒绝、重跑、批准；导出只能读取已批准版本。
- [ ] 每个步骤都能从项目、ExecutionRun、RuntimeRun 或 AuditEvent 追溯。

### G3：Assistant Harness 可靠性

**目标**：把“会聊天”升级为受控的、可恢复的产品操作代理。

验收：

- [ ] 一次用户提交只产生一个用户消息、一个 RuntimeRun 和一条终态；相同 `client_request_id` 重试只回放。
- [ ] Assistant 能在同一轮中完成“查找项目 -> 读取资料状态 -> 启动起草”这类多工具任务。
- [ ] 缺少项目/章节/确认信息时，系统持久化 `needs_input`，下一轮继续，而非猜测或创建空项目。
- [ ] 高风险、写入、成本和删除动作经过 `RuntimeApproval`；拒绝、超时、取消、编辑后恢复均可审计。
- [ ] 后台 workflow 与父 Assistant Run 有稳定关联；前端可以重连后恢复 execution trace。
- [ ] 用户看见面向业务的工具摘要，默认不泄露工具代码名、JSON、ID、原始 provider 内容。
- [ ] 真实模型连续失败时，系统停止并产生安全错误与 Run ID，不无限重试或重复发消息。

### G4：上下文工程与记忆

**目标**：让多轮 Agent 有可解释的上下文管理，而不是无限拼接历史。

验收：

- [ ] Prompt Assembly 具备明确顺序：系统策略 -> 已授权项目上下文 -> 选中的 skills -> 有界会话摘要/近邻消息 -> 附件 -> 有界长期记忆 -> 当前请求。
- [ ] 实现可测试的 Context Compaction：优先保留未完成任务、审批、关键项目绑定和来源；历史对话超过预算时生成/更新摘要，而不是静默截断语义。
- [ ] 记忆写入默认产生 proposal；共享记忆需要批准后才激活；私有记忆只能由所有者读取。
- [ ] 记忆、证据、项目和组织的权限验证均有回归测试。
- [ ] 每次模型调用记录 Prompt/Context policy version、预算和被省略的原因，但不存储密钥或私有原文副本。

### G5：质量、可观测性和安全

**目标**：建立最低可用的效果与安全证据。

验收：

- [ ] 建立至少 20 条脱敏/公开的固定评测案例，覆盖需求提取、检索、引用、工具路由、缺参、审批、跨项目隔离和失败恢复。
- [ ] 评测报告记录代码 commit、模型、provider、prompt/context policy、数据集版本和 hash。
- [ ] 结构性不变量必须为 100%：无跨租户读取、引用 locator 有效、同请求不重复执行、未审批动作不落库、公开错误不含 secret。
- [ ] 质量阈值基于第一轮 baseline 再确定；不编造 Recall 或任务成功率目标。
- [ ] 为一次端到端 Run 关联 Trace/Run ID、耗时、工具次数、模型 token/费用、失败类别。
- [ ] 至少实现一种真实可查询的观测出口：OpenTelemetry/Langfuse 之一，或受控的结构化 Trace 查询页面；不能只保留接口设计文档。

### G6：交付与面试材料

**目标**：任何面试官可在不相信口头描述的前提下理解和验证项目。

验收：

- [ ] README 含本地启动、测试、迁移、Demo 数据导入和演示步骤。
- [ ] 一页架构图说明 Control Plane、Harness、LangGraph、Worker、知识层、审计与外部 Provider。
- [ ] 一页“设计取舍”说明：为何 Harness 不使用 LangGraph、为何 Workflow 使用 LangGraph、为何图谱未投影为事实、为何不引入 Pi SDK。
- [ ] 一份失败复盘：至少说明一个 provider/model/幂等/审批/检索问题的根因、修复和回归测试。
- [ ] 公网只展示脱敏 demo 账户和资料；真实密钥、真实投标文件、隐私数据不进入仓库、截图或演示视频。

## 7. 验收数据与指标

### 固定数据集

- 一个公开或自行编写的脱敏投标资料包；
- 至少 20 个问题/任务；
- 每个案例有期望 requirement、允许的 evidence source、期望工具/审批结果；
- 训练/开发案例与保留回归案例分离；
- 数据集、评测脚本和报告均可追溯到 Git commit。

### 必采指标

| 层 | 指标 |
| --- | --- |
| 检索 | Recall@K、来源 locator 有效率、跨项目拒绝率、降级率 |
| 生成 | 有证据章节占比、缺失证据显式率、人工审核通过/拒绝原因 |
| Harness | 工具路由正确率、缺参暂停正确率、审批正确率、重复执行率 |
| 运行 | TTFT、总耗时、工具次数、失败类别、重试次数、Token/成本 |
| 安全 | 未授权拒绝率、敏感信息泄露测试、Prompt Injection 防护案例 |

## 8. 执行顺序

1. **冻结范围并清理基线**：先完成 G1，不在脏工作区继续堆功能。
2. **跑通黄金闭环**：完成 G2，并录制/记录真实 run。
3. **补 Agent 的持久化上下文**：完成 G3、G4，先 correctness 后体验。
4. **用数据证明效果**：完成 G5，形成可提交的评测与 Trace artifact。
5. **交付与叙事**：完成 G6，再做选择性的前端视觉打磨。

任何新需求都必须回答：它是否让上述一个验收项可证明？若否，进入后续 backlog。

## 9. 风险与决策

| 风险 | 决策 |
| --- | --- |
| 框架热度变化 | 数据模型、事件契约和 adapter 不绑定 LangGraph/Provider |
| 过度扩张 | 只做 BidPilot 一个项目闭环 |
| 模型不稳定 | Provider adapter、结构化工具调用、红acted 失败、固定回归集 |
| 幻觉 | 检索引用、missing-evidence、人工审核，不承诺“零幻觉” |
| 注入攻击 | 文档/附件视为不可信上下文，工具权限与系统策略分离 |
| 记忆污染 | proposal + 证据 + 审批；不自动把模型输出变成事实 |
| 演示不可复现 | 固定资料、环境变量清单、demo 脚本、数据库迁移、质量报告 |

## 10. 完成定义

本 Spec 只有在 G1-G6 全部满足、固定 demo 成功重复三次、回归测试与质量门禁可复跑后才标记完成。

完成后的简历表述应使用“实现/设计/验证”而不是“行业首创/生产级自治平台”。
推荐表述：

> 设计并实现投标文档智能执行平台 BidPilot：基于 FastAPI、PostgreSQL/pgvector、Redis/Celery、LangGraph 与受控 StreamingHarness，实现证据检索、工具调用、HITL 审批、可恢复工作流、受治理记忆、SSE 执行追踪和离线质量门禁。

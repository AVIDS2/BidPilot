# BidPilot Claim Integrity Runtime Capture

## Status

- Date: 2026-07-22
- Status: implemented and locally regression-verified
- Depends on: Claim Integrity v1, BidBench v2.1, Requirement Ledger, Runtime
  workflow bridge, and controlled evaluation provenance

## Problem

`claim_trace_integrity_rate` is meaningful only when a candidate represents a
real governed workflow. A hand-authored JSON candidate can hide an incorrect
requirement/evidence/claim topology, while exporting a normal project snapshot
would expose customer claim text, evidence quotations, locators, document
names, and durable database identifiers.

## Decision

Provide an offline, read-only capture adapter:

```text
private reviewed manifest
  -> successful draft/redraft ExecutionRun
  -> generated SectionVersion + Claim topology
  -> succeeded Runtime workflow bridge
  -> redacted BidBenchCandidate
```

The manifest stays outside generated artifacts. It maps only durable runtime
IDs to frozen benchmark IDs or evaluator-chosen opaque candidate IDs. It does
not contain source text, claim text, evidence quotes, locators, model payloads,
or secrets.

## Capture Contract

One manifest captures one project snapshot bound to one successful
`draft_section` or `redraft_section` run and its generated section version.
The capture validates all of the following before emitting any candidate:

1. the manifest dataset and canonical fixture fingerprint match the frozen
   BidBench dataset;
2. the ExecutionRun succeeded, belongs to the mapped project, produced the
   mapped section version, and records Claim Integrity output;
3. the section version is generated by that run and belongs to the mapped
   project;
4. exactly one successful workflow-bridge RuntimeRun points at the execution
   run and has the same organization/project scope;
5. the private manifest exactly covers current project Requirements, all
   support evidence and Claim evidence references reached by those records,
   and every Claim created by that execution run; and
6. all benchmark source, requirement, and evidence references used by the
   mapping exist in the frozen dataset.

The capture does **not** require every Claim to be structurally correct. A
missing support pair, an unknown mapped evidence ID, or a mismatched
requirement is encoded as a safe unmatched candidate value so BidBench records
the failure. A capture only rejects missing, ambiguous, out-of-scope, stale, or
incompletely mapped provenance.

## Redaction Rules

The generated candidate can include only:

- frozen dataset labels and IDs;
- evaluator-supplied opaque candidate IDs;
- enum values and numeric confidence/latency/cost metadata; and
- reviewed provenance metadata.

It never includes runtime project/organization/user/ExecutionRun/RuntimeRun/
SectionVersion/Requirement/Evidence/Claim IDs; claim text; requirement text;
source document names; raw locators; evidence quote text; prompt/model output;
or hidden reasoning. Candidate Claim text is a deterministic opaque placeholder
because this capture evaluates structural provenance, not semantic claim truth.
Any candidate identifier that reuses a durable runtime identifier is rejected
before serialization.

## Metric Semantics

The emitted `BidBenchCandidate` still derives requirement type, coverage,
evidence links, and accepted Claim state from the durable product records. A
runtime requirement is credited with a benchmark-normalized text or locator
only after its private mapped data matches the frozen benchmark record. A
mismatch becomes an opaque unmatched value, preserving false positives and
false negatives in the normal BidBench score.

For every Claim, requirement and evidence references use the opaque candidate
IDs. The existing `claim_trace_integrity_rate` then evaluates the full mapped
requirement/evidence cross-product. No capture layer creates, verifies,
upgrades, or removes Claims.

## Operational Guardrails

- There is no API endpoint, background task, or browser path for runtime
  capture.
- The CLI requires an explicit redaction acknowledgement and writes only below
  the repository `output/` directory.
- The manifest is supplied explicitly and is not copied into the candidate or
  report.
- A controlled release capture requires `current_pipeline` provenance and a
  two-person review attestation. Development fixtures remain non-release
  evidence.

## Operator Usage

The private manifest must remain outside the repository, generated candidate,
and benchmark report. From the repository root, an operator supplies the
reviewed dataset and manifest explicitly:

```powershell
uv run --directory services/api python ../../scripts/capture_claim_integrity_runtime_bench.py `
  --dataset <frozen-dataset.json> `
  --manifest <private-reviewed-manifest.json> `
  --output-file output/claim-integrity-runtime-candidate.json `
  --confirm-redacted-claim-capture
```

The resulting candidate can be evaluated with the normal BidBench CLI. Capture
does not set a release threshold, alter a Claim, or enable an export gate.

## Non-Goals

- no semantic NLI claim judge;
- no automatic Claim verification or export gating;
- no capture of existing customer projects without a reviewed private mapping;
- no source-text anonymization heuristic; and
- no replacement for retained CI/VPS execution evidence.

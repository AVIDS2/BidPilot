## Agent UI and runtime rule (2026-07-25)

The product must not treat Agent UI as a generic chat widget. It is the visual
projection of a durable execution trace. Do not make isolated visual fixes or
swap component libraries before the execution contract and acceptance states
are defined.

### Required implementation order

1. Define and version the Agent Run event contract before implementation.
   Every event needs stable `run_id`, `event_id`, `sequence`, `timestamp`, and
   an optional `parent_id`.
2. Provide typed events for at least: `run.started`, `plan.updated`,
   `tool.started`, `tool.progress`, `tool.completed`, `tool.failed`,
   `approval.requested`, `approval.resolved`, `message.delta`,
   `message.completed`, `run.cancelled`, and `run.completed`.
3. Build a frontend state gallery using fixtures before wiring live SSE:
   idle, planning, running, streaming, approval, failed, cancelled,
   background-completed, and restored-session.
4. Implement backend producers and frontend consumers against the same
   contract. Avoid optimistic duplicate messages and deduplicate by event ID.
5. Verify visual behavior at desktop and mobile sizes before deployment.

### UX requirements

- Prefer an independent `/agent` workbench for the full interaction. A sidebar
  is an entry point, not the full execution surface.
- Render activity as a compact execution summary followed by expandable,
  chronological trace rows. Never leak raw tool payloads, internal tool names,
  or JSON by default.
- Approval, cancellation, background execution, artifacts, retries, and
  failures are first-class states, not text embedded in an assistant message.
- Use a coherent design system and exact visual references. A library does not
  automatically provide its demo-level visual quality.
- Avoid stacks of decorative cards, arbitrary palette changes, hard-coded
  widths, and changes that are not checked against overflow and responsive
  layouts.

### Dependency policy

- `@jetv/chat-widget` may be studied for ideas only. It is too new and lacks
  public source, license, and declared repository metadata, so it must not be
  a core production dependency.
- Evaluate mature libraries only through a contained proof of concept using
  the real event contract. Do not transplant a chat library across the product.

### Working agreement

Before further Agent UI or runtime changes, read this file and present the
event contract, fixture coverage, and acceptance criteria. Do not deploy
unverified visual changes merely to iterate in production.

## Backend Runtime P0 Baseline (2026-07-26)

- Public assistant requests use one governed `StreamingHarness` path. The old
  LangGraph operator is not a public fallback; LangGraph remains the durable
  worker workflow runtime for bid pipelines.
- Each browser turn carries `client_request_id`. Retry replay is backed by a
  user-scoped idempotency key and a unique durable `RuntimeRun`.
- Missing tool fields persist a `needs_input` task state; approvals persist
  `RuntimeApproval`; workflow launches create linked bridge runs.
- Runtime event contract is schema `1.1` with event lineage and monotonic
  sequence. UI must consume this trace, not construct optimistic fake states.
- Provider/model construction and in-loop failures must produce redacted,
  durable SSE terminal events. Never surface raw gateway responses to users.
- Current regression baseline: 191 assistant/runtime/chat/OpenAPI tests pass
  in the isolated Docker test database. Re-run this suite before deployment.

## P0 Candidate Review and LangGraph Resume Closure (2026-07-27)

- A quality-passed LangGraph draft is now persisted first as an immutable
  `SectionVersion` review candidate. The section and its deliverable move to
  `in_review`; export remains pinned to the prior `approved_version_id` until
  a human explicitly approves the candidate.
- Each candidate has a durable `ReviewThread`, linked by `section_version_id`.
  A review decision reuses that thread, writes an audit event, and cannot
  silently approve or export a different/latest version.
- A final candidate decision is immutable: a repeated identical request is a
  no-op (no second notification or outbox event), while an opposite decision
  fails with `409 review_decision_already_finalized`.
- Approving or rejecting a workflow-created candidate writes exactly one
  sequenced `worker.resume_draft` outbox intent after the decision transaction
  commits. Rejecting preserves an earlier approved snapshot; the resumed graph
  may create a new candidate in the same execution run.
- `SectionVersion.generation_iteration` plus
  `uq_section_version_run_iteration` provides idempotency per
  `(section, execution run, iteration)`: retrying a pause does not duplicate a
  candidate, while a post-rejection revision remains a distinct immutable
  version. The migration repairs legacy duplicate run versions by assigning
  stable iterations before adding the constraint.
- LangGraph's approval interrupt now includes `section_version_id` in its
  durable runtime event; the API SSE schema documents the same review target.
- `PostgresSaver` checkpoint tables are now initialized as an explicit one-shot
  Compose dependency and in the fallback deployment path after Alembic. Worker
  tests invoke the same initializer against the isolated `*_test` database;
  runtime code never lazily creates checkpoint tables during a user request.
- Verification in isolated PostgreSQL: migration downgrade/upgrade through
  `b2c3d4e5f6a7` succeeded; Worker graph/task/outbox regressions: `38 passed`;
  API review/drafting/bridge regressions: `12 passed`; API runtime contracts:
  `91 passed`; targeted Ruff checks, `bash -n deploy.sh`, and
  `docker compose -f compose.yml config --quiet` all passed. No public
  deployment was performed.

## P0-B3 Requirement / Compliance Read Model Closure (2026-07-27)

## P0-C1/C2/C3 Assistant Runtime Reliability Closure (2026-07-27)

  a duplicate `client_request_id` replays the durable `RuntimeRun` trace
  instead of creating another chat message, model call, or capability action.
- The public Harness performs a bounded, result-driven capability loop. A

  resolve the outline, and bridge into a drafting workflow without exposing

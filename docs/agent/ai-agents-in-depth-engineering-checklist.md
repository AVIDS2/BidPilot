# 《深入理解 AI Agent》工程检查表

来源：`F:/QQ下载文件/AI-Agents-in-Depth-zh-CN.pdf`，v1.3（2026-07-29）。本文是对原书的工程映射，不替代原书。

## 1. 必须守住的模型

原书将 Agent 拆为 LLM、上下文和工具。对 BidPilot 来说，最容易被忽略的是“上下文”并不等于聊天记录：它还包括当前项目、已确认的资料、工具结果、运行状态、权限和用户的待答信息。

- 工具调用不是终点。结果、错误、耗时和产物定位必须回到下一轮模型上下文，也必须在用户界面可查。
- 对咨询、解释和比较问题，先直接回答；只在需要真实数据、改变状态或用户明确要求导航时调用工具。
- 高风险写操作维持专用工具、参数校验、数据库真值校验和人工确认；不把业务规则只写进系统提示词。
- 通用能力可以组合探索，业务写入和交付仍由受限工具完成。这样既不把 Agent 锁死在业务流程，也不让它绕过审计边界。

## 2. ReAct 与 Harness

每个回合应保持下面的可观察闭环，而不是“模型输出一段文字后就标记完成”。

```text
观察上下文 -> 规划/推理 -> 工具调用 -> 工具结果或错误 -> 更新上下文 -> 决定继续、暂停或回答
```

Harness 负责上下文构造、工具协议、执行、安全、验证、恢复和持久化；LangGraph 仅在需要长任务/明确节点编排时承接执行，不应成为业务真相来源。

当前已落地：

- `HarnessLoop` 维护模型回合、工具调用、成功/失败、暂停和持久化事件。
- `assistant.tool_started/progressed/succeeded/failed` 映射到前端连续事件流。
- `assistant.missing_input` 与确认事件为可恢复暂停，而非失败或空等。
- 只有执行器显式允许、工具声明 `parallel_safe`、且没有共享的 `prepare` 阶段时，Harness 才并行执行独立工具。BidPilot 的写业务适配器继续串行。

仍需逐项验收：

- 每个业务工具是否都声明了读写属性、幂等键、超时、重试策略和可展示错误码。
- 每个工具结果是否既进入下一回合上下文，也有用户可读摘要和可展开的脱敏原始结果。
- 长任务的运行恢复是否能在新会话/刷新后接续，而不依赖内存中的流连接。

## 3. 状态栏和异步回调

原书把状态栏视为 Agent 的轨迹管理元信息。产品状态不能只有加载三点或“已完成”，需要明确且互斥地呈现：

| 运行状态 | 用户可见含义 | 恢复方式 |
| --- | --- | --- |
| `thinking` | 正在理解或规划，尚未开始工具 | 等待下一事件 |
| `executing_tool` | 正在调用具体工具 | 实时进度、成功或失败事件 |
| `running_workflow` | LangGraph 长任务正在节点执行 | SSE/轮询回放运行事件 |
| `needs_input` | 缺少字段，任务暂停 | 填写结构化表单后在原会话继续 |
| `needs_confirmation` | 有影响外部世界的动作待批准 | 批准或取消 |
| `failed` | 有错误码、原因和重试入口 | 修正参数/恢复点/重试 |
| `completed` | 本轮没有待运行、待确认或待补充事项 | 新一轮请求 |

当前已落地：

- Agent 顶栏显示上述即时状态，运行态有轻量活动标记。
- 缺少项目名、链接、章节等字段时，前端渲染受控表单；通用 `assistant.end` 不能覆盖 `needs_input`、`needs_confirmation` 或 `failed`。
- 工作流、工具和模型事件有独立 span；运行中、成功、失败和重试不是同一个“完成卡片”的不同文案。

## 4. 工具与事件协议

工具协议至少携带：`trace_id/run_id`、`turn_id`、`tool_call_id`、工具名、脱敏参数、状态、结果或错误码、时间戳和重试次数。前端不能依赖 LLM 叙述猜运行结果。

当前事件分层参考 Pi/OpenCode：文本、推理、工具输入、工具开始、进度、成功、失败、重试、人工暂停和工作流节点各自独立。时间线以连续竖线和状态点呈现；用户展开后可见脱敏的“工具输入与返回”。

对于 Agent 生成的界面动作，使用受限的 `ui_action`，不是由自然语言触发任意跳转：

- `canvas`：显示“打开任务编排画布”按钮，用户点击后进入当前项目的编排画布。
- `link`：仅允许应用内部、白名单路由。
- 交付物：展示真实下载入口，不把内部路径当作最终答案。

## 5. 上下文、提示词和首 Token 延迟

- 保持系统提示词和工具定义的稳定前缀，把项目状态、时间、检索结果和用户输入追加在动态尾部，以保留 KV/prompt cache 命中。
- 提示词写任务边界、决策规则和工具使用时机，不堆叠所有业务细节；业务不变量放在工具和数据库校验中。
- 工具描述应包含用途、参数、前置条件、禁止情形、成功定义和失败恢复方式。模糊描述会直接造成误调用。
- 只装入当前任务相关的资料/检索片段/运行状态；不要把全量项目或全量工具塞入模型。

## 6. Trace、评估与验收

原书强调评估对象是“模型 + Harness”。因此不以单次对话看起来通顺作为验收。

每个场景都应同时检查：

1. 最终业务结果：项目、资料、章节、交付物是否真实写入并可在产品入口找到。
2. 过程正确性：工具是否被必要且正确地调用，独立读操作是否并行，写操作是否没有越权或重复。
3. 可恢复性：工具超时、参数不全、用户拒绝、刷新页面、外部回调迟到后是否有明确状态和恢复入口。
4. 可观测性：同一 `trace_id` 下能关联模型、工具、数据库/工作流 span、参数摘要、结果、耗时、错误码和产物。
5. 交互质量：咨询不乱调工具；等待时能看见原因；缺信息用表单；导航/下载/画布以按钮或链接呈现。

建议把这些场景沉淀成固定数据集，按模型版本、提示词版本、工具版本、并行开关和权限模式运行；新增能力或换模型必须跑回归，不能只看演示成功率。

# 科大讯飞智能招采调研、BidPilot 定位与第一轮落地计划

> 日期：2026-08-14  
> 状态：调研完成，作为后续实现的产品与验收基线  
> 范围：BidPilot（投标响应方工作台），不把采购方的评标/监管系统误纳入当前核心范围。

## 1. 结论先行

BidPilot 应定位为 **面向投标、售前与方案交付团队的 B2B 文档交付操作系统**：SaaS 的日常体验、私有化部署的安全边界、开源上游的可替换能力底座。它不是聊天套壳，也不是采购侧电子交易平台的复刻。

科大讯飞的公开产品证明了两件事：

1. 招采产品的价值不来自页面上的“Agent 数量”，而来自清楚可见的业务阶段、证据链、规则校验、人机复核和可落地部署。
2. “对话驱动任务”可以降低复杂流程的使用门槛，但每一个任务仍必须落回可见的项目、资料、要求、交付物、审批和审计对象。

因此，BidPilot 的第一优先级不是去做采购方的“辅助评标/围串标监管”，而是把供应商侧的“发现机会 -> 获取材料 -> 建模要求 -> 准备证据 -> 起草 -> 审查 -> 交付”闭环做成可操作、可恢复、可审计的产品。

### 指标澄清

- 已找到的公开“97%”口径是 **客观项评审准确率**，属于采购评审子任务；不是“全流程精确度”。
- 本次未找到可信公开来源支持“90% 投标交付率”。不应在 BidPilot 介绍、销售材料或验收报告里使用该数字。
- BidPilot 必须用自己的项目级基准集记录：要求提取 Precision/Recall、证据覆盖率、人工修改率、审批一次通过率、导入成功率、任务恢复成功率与完成耗时。

## 3. 竞品真正值得借鉴的设计

### 3.1 业务阶段是产品骨架，不是功能罗列

讯飞把复杂招采映射为固定阶段和专业角色，用户始终知道任务正在哪一段。BidPilot 也要采用同样原则，但改为供应商侧闭环：

```mermaid
flowchart LR
  A[机会雷达] --> B[项目立项]
  B --> C[资料中心]
  C --> D[要求与评分点]
  D --> E[响应计划]
  E --> F[章节与证据]
  F --> G[质量审查]
  G --> H[导出与交付]
  A -.发现来源.-> C
  H -.复盘为可复用资产.-> E
```

每个阶段都必须展示：当前责任人、可执行动作、阻塞原因、来源证据、下一步，而不是只展示一张静态流程图。

### 3.2 “可信”来自结构化约束，不来自模型自称完成

可借鉴的是“理解含义 -> 找到证据 -> 按规则计算/判断 -> 人工复核”的链路。对 BidPilot 应落实为：

- 要求项必须链接原文位置，缺证据必须显式标红；
- 章节草稿必须给出引用或“证据缺失”状态；
- 合规检查先跑确定性规则，再由模型解释风险；
- 审批、导出和远程资料入库必须有业务记录，不能只存在聊天上下文。

### 3.3 部署与接入是 B2B 产品的一部分

竞品将公有云、私有化、OA/SRM/ERP 对接、API 作为产品能力。BidPilot 的差异化不能是“又一个封闭平台”，而应是：

- **Community / 上游版**：Docker Compose 一键部署、默认本地对象存储、可选模型/搜索/解析适配器；
- **私有化版**：同一镜像与同一业务合同，企业在自有网络接入模型、OCR、对象存储、SSO、邮件和外部资料源；
- **云服务版**：托管运维、租户隔离、计量和支持；核心业务不能分叉。

## 4. BidPilot 的产品心智：用户到底在和谁交互

当前技术上存在 Harness 与 LangGraph 两条执行路径，但产品没有把它们命名和解释清楚。这正是“我不知道 LangGraph 编排 agents 是谁”的原因。

| 用户看到的名称 | 技术实现 | 用户如何使用 | 它负责什么 | 它不负责什么 |
| --- | --- | --- | --- | --- |
| **BidPilot 助手** | Harness / ReAct 工具循环 | 在“智能体”对话中提问、上传、发起动作、确认审批 | 识别目标、提出计划、调用受治理的能力、解释结果 | 不伪造完成，不直接拥有业务状态，不执行服务器任意命令 |
| **交付运行** | LangGraph + Worker + ExecutionRun | 在项目“交付”或“响应计划”中发起，查看阶段、暂停、审批、恢复和结果 | 长任务：解析、要求建模、起草、审查、导出 | 不是一个需要用户聊天的虚拟人；checkpoint 不是业务真相 |
| **工作角色模板** | 受限 Skills + 工作流节点 | 在交付运行的阶段中出现，例如“资料建模”“合规审查” | 为一个步骤提供领域提示、工具范围和验收规则 | 不是为了凑数而创建的独立 Agent 进程 |

对外文案统一使用“交付运行”，只在技术说明、日志和开发者页面出现 LangGraph。首批工作角色模板固定为：机会研判、资料建模、要求审查、章节起草、交付质检。它们会在不同项目中按任务需要启用，不宣传为“上百个 Agent”。

## 5. 现有基础与不能再回避的缺口

| 能力 | 当前基础 | 缺口/下一步 |
| --- | --- | --- |
| Harness | 已有 `StreamingHarness`、受治理 capability、SSE、审批暂停、幂等重放 | 状态栏需明确“运行/等待输入/等待审批/等待外部任务/已恢复”；失败需有可行动原因 |
| 长任务 | 已有 Worker LangGraph、`ExecutionRun`、检查点和审批恢复 | 以“交付运行”形成项目入口、阶段视图、节点责任与恢复动作 |
| Trace | 已有 `RuntimeRun`、有序 `RuntimeEventRecord`、父事件链路 | 补齐 trace/span 语义、跨 API/Worker 的关联 ID、耗时/重试/等待原因，并面向用户展示安全摘要 |
| 记忆 | 已有受治理 MemoryRecord、证据链接与检索边界 | 对话上下文压缩、会话摘要、跨会话“继续此任务”入口必须可见且可控，不能把业务真相塞入摘要 |
| 远程资料 | 已有受限的服务端直链下载器和本地 companion downloader 原型 | 区分“发现公告页”与“导入附件”，记录来源、MIME、哈希、失败类别、确认动作；不能把网页抓取冒充附件下载 |
| 私有部署 | 已有 Compose 基础、适配器边界 | 形成发行镜像、最小生产配置、密钥/SSO/对象存储/模型/OCR 搜索适配器清单与升级策略 |

## 6. 第一轮 1/2/3 的实施计划

这三项按依赖顺序完成。每一项都包含用户入口、后端契约、失败状态和浏览器验收；不接受“后端已有、前端找不到”的完成定义。

### 1. 远程资料来源与下载链路

**目标**：用户从雷达、公告页或助手发现附件后，能看见“候选资料”，检查来源和文件类型，经确认后导入项目资料包；失败可诊断、可重试，不靠模型反复搜索或猜 URL。

**实现任务**：

1. 定义 `ExternalMaterialCandidate`：公告页 URL、附件直链、显示名、来源站点、发现时间、MIME/大小（若可探测）、证据和规范化 URL。
2. 将“网页抓取”和“二进制附件下载”分成两种工具及两种状态。网页只用于发现；仅 `pdf/doc/docx/xls/xlsx/zip` 等允许作为附件导入。
3. 导入前展示候选资料卡；确认后走受限 downloader，流式下载、大小上限、重定向/SSRF 防护、HTML 拒绝、哈希去重、对象存储原子提交。
4. 返回稳定错误码：`unsupported_content`、`requires_login`、`source_unavailable`、`too_large`、`duplicate`、`policy_denied`；助手只根据该错误决定下一步，禁止擅自改协议或无限重试。
5. 编写本地 HTTP fixture：正常 PDF、ZIP、HTML 伪装、重定向、超限和断流；不把真实政府站作为 CI 依赖。

**验收**：浏览器和自然语言各导入一次真实直链格式的文件，均能在资料页打开来源和状态；六类异常均有明确可行动提示。

### 2. 本地 Companion 产品化入口

**目标**：需要本地受控下载或本地文件采集时，在用户机器执行，而不是把服务器 shell 权限交给模型。

**实现任务**：

1. 将现有 downloader 原型封装成独立 companion 协议：版本、健康检查、受支持操作、用户选定目录、host allowlist、下载进度和结果回执。
2. 在资料中心和助手审批卡提供“使用本机 Companion 保存/导入”的入口；未安装时给出安装和连接状态，而非假装已执行。
3. 每次执行展示 URL、目标目录、文件名、大小限制、网络域名和确认记录；仅返回上传后的 artifact 或签名结果，不允许服务端下发任意 shell 字符串。
4. 设计 CLI/桌面守护进程的 Docker 外发布方式、版本兼容和离线诊断。第一版不做任意命令执行。

**验收**：用户选择目录，Companion 下载合法文件并回传资料包；拒绝未确认目录、非白名单域名、HTML 内容和超限文件；服务端容器无本机文件系统权限。

### 3. 多角色预发布验收与可观测性闭环

**目标**：用真实的用户角色和异常态证明闭环，而不是只跑单元测试。

**实现任务**：

1. 以四个角色编写 Playwright/API 验收：项目经理、方案工程师、审查人、组织管理员；包含无权限、审批拒绝、导入失败、模型失败、任务恢复、导出失败。
2. 给每个助手回合和交付运行分配统一 `trace_id`；产生 API、模型、工具、队列、LangGraph 节点 span，记录安全摘要、耗时、状态和父子关系。
3. 增加用户可读的运行状态栏：当前动作、已用时间、等待对象、可执行恢复/取消/重试；后台任务完成后通过事件唤醒，而不是模型轮询“完成了吗”。
4. 产出一份可复现的预发布报告：用例、版本、种子、结果、失败产物、已知限制；P0 的安全、幂等、终态或跨租户失败直接阻塞发布。

**验收**：至少一条完整供应商侧黄金链路和全部异常矩阵可重复运行；每个失败都能从业务页面跳到安全的 trace 摘要，管理员可进一步查看诊断。

## 7. Agent 运行时收口要求（与 1/2/3 并行约束）

这不是再造一个“大而全 Agent 平台”，而是给已有 Harness 和交付运行补齐可恢复语义：

1. **状态机**：`running`、`waiting_input`、`waiting_approval`、`waiting_workflow`、`resuming`、`succeeded`、`failed`、`cancelled`。任何等待不是失败，任何失败必须有稳定原因。
2. **事件唤醒**：Worker/审批/导入完成写入事件，由 run subscription 唤醒后续阶段；模型不会主动无限轮询。
3. **跨会话继续**：新会话可以选择“继续某次交付运行”，加载经授权的任务摘要、未完成 action 与可公开 trace，不复制整段原始对话，也不越过项目边界。
4. **上下文压缩与记忆**：压缩的是对话材料，业务事实仍从 PostgreSQL/资料/要求/交付物读取；长期记忆必须有来源、作用域、审批和撤销。
5. **Trace/Span**：Trace 表示一次用户目标的全链路；Span 表示模型调用、工具、API、队列、节点、下载或审批等待的一步。用户看摘要，运维在授权下看诊断。
6. **提示词**：提示词只描述角色、目标、证据优先、工具选择和用户语言；参数校验、审批、重试、幂等、取消、权限和终态由运行时合同保证。不得靠长提示词掩盖后端不确定性。

## 8. 后续产品信息架构与分期

| 近期（完成 1/2/3 后） | 中期 | 不纳入当前 BidPilot 核心 |
| --- | --- | --- |
| 雷达、项目、资料、要求、响应计划、交付、交付运行、审查、集成 | 企业资产库、投标复盘、来源连接器市场、可配置审查规则、私有化发行包 | 采购方定标、专家抽取、围串标执法监管、ERP 替代、泛化无代码工作流产品 |

页面不应再堆重复跳转卡片。每一个导航项对应一个稳定业务对象和下一步操作；每一项自动化均能回到人能读懂的项目状态和证据。

## 9. 决策记录

1. BidPilot 固定为供应商侧投标响应与交付工作台；只复用采购侧竞品的证据、规则、审查、可追溯和私有化思想。
2. 交付工作流的产品名固定为“交付运行”，LangGraph 只作为实现技术出现。
3. “Agent 数量”不作为路线图 KPI；首批只维护五个可解释的工作角色模板。
4. 远程附件导入先保证受控服务端直链和本机 Companion 两条边界清晰的路径，不开放服务器任意网络/命令。
5. 发布材料不得使用未经自身基准验证的“准确率/交付率”营销数字。

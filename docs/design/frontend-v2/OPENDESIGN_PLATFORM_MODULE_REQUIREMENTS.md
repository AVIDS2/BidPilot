# BidPilot OpenDesign 全平台前端原型需求

> 状态：交给 OpenDesign / Claude Code 的设计输入。
>
> 目标：先完成可评审的高保真产品原型，再开始 React V2 重构。此文档定义模块、状态、
> 信息架构和验收，不要求在原型阶段接入真实 API。

## 1. 产品一句话

BidPilot 是面向投标经理、售前工程师、方案架构师和交付负责人的 **AI 投标执行工作台**。
它把资料、要求、证据、草稿、审查、交付和审计组织进一个可协作、可追溯的项目空间。

它不是“上传 PDF 后问问题”的聊天壳，也不是泛化的工作流编排器。

## 2. 原型阶段的边界

### 要做

- 建立全平台信息架构、设计 token、组件规则和关键交互原型；
- 覆盖公开营销站与登录后的企业工作台；
- 覆盖桌面、平板和移动端；
- 覆盖 Agent、知识库、项目协作、运行/审批/失败恢复等真实复杂状态；
- 使用与实现一致的真实领域文案和 fixture 数据。

### 不做

- 不修改现有 React V1 页面；
- 不部署到公网；
- 不伪造真实客户、认证、使用量或效果数据；
- 不把技术内部名、JSON、SQL、栈追踪或模型参数直接展示给终端用户；
- 不为炫技而加入 3D、粒子、渐变光球、持续呼吸或假“AI 思考”。

## 4. 用户、任务与设计优先级

| 用户 | 最频繁的任务 | 设计必须优先保证 |
| --- | --- | --- |
| 投标经理 | 建项目、分配资料、看风险和进度、确认关键动作 | 全局态势、待办、审批与审计 |
| 售前/方案工程师 | 找证据、起草章节、修订、提交审查 | 资料可追溯、草稿与引用并存 |
| 审查人 | 阅读草稿、定位依据、评论、批准或驳回 | 低认知负担的证据、diff 和决策 |
| 知识管理员 | 维护共享资料、同步、修复解析、控制权限 | 作用域、生命周期、质量与访问控制 |
| 管理员 | 管成员、模型、知识连接、成本/运行风险 | 受限配置、日志、健康态与恢复 |

用户的主路径必须可在 60 秒内理解：

```text
新建项目 -> 上传资料 -> 解析/建立知识 -> 检查要求与证据
-> 发起草稿 -> 审查/批准 -> 导出交付物 -> 查看审计
```

## 5. 全局信息架构

### 已登录工作台导航

顶层主导航仅保留真正高频且有独立工作对象的区域：

```text
概览
项目
智能体
知识资产
运行记录
----------------
团队与成员
模型提供商
审计与治理
账户与账单
```

- “文档”“定价”等公开站入口不出现在工作台主导航；
- Settings 不应是一个塞入所有功能的黑洞；
- 任何二级动作放入所属模块工具栏、溢出菜单或详情页；
- 桌面左栏 232-264px，收起后 64-72px；主区域真实扩展，绝不被遮住；
- 768px 以下把主导航、会话与上下文改为 Drawer/Sheet，不保留挤压的细长栏。

### 项目工作台二级结构

```text
项目概览与下一步
资料与来源包
要求与证据
草稿
审查
交付物
审计
```

不得把十几个无关 tab 等权平铺。项目设置、成员、模型覆盖和归档属于项目 Header 的
受控菜单，而不是一个新的主 tab。

## 6. 模块需求

### A. 公开站：Landing、定价、文档、认证

#### Landing

目标不是堆“AI 能力”，而是在首屏解释真实收益：让团队把招标资料变成可验证、可审查、
可交付的投标执行过程。

必须模块：

1. 清晰的产品名称与一句话价值；
2. 真实工作流展示：资料 -> 要求与证据 -> 草稿 -> 审查 -> 交付；
3. 三到四个可验证能力：来源追溯、团队协作、受控 Agent、审计交付；
4. 安全/私有部署/权限的简洁说明，不能伪造 SOC2、客户 logo 或指标；
5. 明确 CTA：创建工作区 / 预约演示；
6. 页脚中的产品、资源、法律和联系入口。

#### 定价与文档

- 定价页以真实套餐和能力边界为准；无真实支付能力时展示“联系团队”，不伪造 checkout；
- 文档页是产品帮助中心，不得与开发者 API 文档混成一页；
- 登录/注册页要有信任和隐私文案，但不能写虚假的认证或 SSO 已可用。

### B. App Shell 与 Dashboard

#### App Shell

- 平滑 SPA 路由，局部 skeleton，禁止整页白屏；
- 命令面板可查找项目、知识资产、运行、设置；
- 有一致的 Header、Breadcrumb/Project context、通知与账户菜单；
- 侧栏收起需重新布局，不得以 absolute 覆盖主内容；
- 键盘焦点、tooltip、Esc 关闭和滚动锁定必须可设计与验证。

#### Dashboard

空态不可只放一个“创建项目”按钮。必须提供下一步漏斗：

```text
创建/导入项目 -> 上传资料包 -> 等待解析 -> 检查要求 -> 发起第一段草稿
```

有数据时显示能操作的内容：

- 最近项目及其当前阶段；
- 待确认审批；
- 运行中的任务与失败重试入口；
- 待审查草稿或交付物；
- 最近活动和证据/资料风险。

### C. 项目与项目工作台

#### 项目列表

- 表格/列表优先，支持搜索、筛选、排序、状态、负责人、最后活动；
- 创建项目是明确 dialog/form，含模板/场景、名称、团队和资料引入；
- 不要用没有信息价值的大图卡片。

#### 项目概览

- 项目名称、状态、负责人、截止日期、资料健康度、下一步；
- 活动时间线、风险、运行和待审批项；
- 用户从此处可立即进入资料、要求、草稿或 Agent。

#### 资料与来源包

- 拖拽/选择/批量上传；
- 文件是独立对象，不塞进聊天气泡；
- 状态必须真实：待上传、上传中、已上传、解析中、可检索、失败、需处理、已归档；
- 显示文件类型、大小、来源、作用域、解析时间和可用操作；
- 支持预览、重新解析、替换、归档/删除；危险操作有确认与审计；
- 无法读取的文件不能被 Agent 宣称“已分析”。

#### 要求与证据

- 左侧要求矩阵，右侧支持证据与来源定位；
- 要求必须有状态：未覆盖、部分覆盖、已覆盖、存在冲突、需要人工确认；
- Evidence 展示原文片段、文件、页码/段落、检索时间、适用范围与置信信号；
- 不用“图谱”替代真实证据列表。

#### 草稿与审查

- 草稿按章节和版本组织；
- 每个段落可展开来源、改动原因和生成 run；
- 审查使用可调整的左右分屏：草稿/证据与评论/决策；
- 支持评论、@成员、批准、驳回、要求重写和版本 diff；
- 每个决策须留下人、时间、理由与关联版本。

#### 交付物与审计

- 显示交付物、版本、导出格式、生成时间、审批状态和下载；
- 审计按人类事件表述：上传资料、启动起草、批准章节、导出交付物；
- 技术 trace 放在受控的“技术详情”中，不向一般用户抛原始日志。

### D. 知识资产：以 WeKnora 为知识引擎

知识资产是独立主模块，但必须与项目工作台和 Agent Desk 连通。

#### D1. 知识资产主页

展示两类明确分开的资产：

```text
组织共享知识
项目专属知识
```

每条资产显示：作用域、资料数量、健康状态、最后同步、权限、检索可用性。用户可以进入
知识库、搜索、导入资料、查看 Wiki、检查同步或管理权限。

#### D2. 知识库详情

三区布局：资料树/筛选、内容或检索结果、详情/引用侧栏。

支持：

- 文件、URL、Markdown、同步连接的导入入口；
- 解析队列、失败原因、重试和重解析；
- 标签、文件夹、来源、更新时间和所有者；
- 受控的检索配置摘要，默认不暴露低层向量参数；
- “以此知识库问答”入口，进入 Agent Desk 且携带范围。

#### D3. Wiki

- Wiki 是从资料归纳出的可读 Markdown 知识页面，不是聊天摘要堆；
- 有树形导航、页面正文、关联来源、最近更新和需要复核标记；
- 自动生成/刷新 Wiki 必须是一个可追踪 run；
- 用户可标记页面为已确认、需要更新或禁止作为默认证据。

#### D4. 知识图谱

- 仅在 WeKnora 返回真实节点与边时展示；
- 使用 2D 交互图和列表/搜索作为同等可用的替代，不做纯装饰 3D 球；
- 节点至少分为文档、实体、要求、方案能力、人员/案例、Wiki 页面；
- 单击节点显示来源、关系理由、最后更新和“在 Agent 中询问”；
- 支持按项目/组织、类型、时间、置信度筛选；
- 大图默认聚合，避免一打开就数百节点失控。

#### D5. 检索试验与质量

给管理员/知识管理员使用：输入问题、选择范围，展示检索命中和引用，不展示模型内部思维。
可以查看资料是否命中、是否过期、是否缺失，但质量指标只能显示真实计算结果。

### E. Agent Desk：最高优先级

`/agent` 是完整的独立页面；其他页面的浮动 Agent 只是打开它或带上下文跳转的入口。

#### 布局

```text
全局导航 | 会话历史 | 对话与执行轨迹主列 | 可选项目/证据/产物上下文栏
```

- 会话历史可收起、独立滚动，支持新建、搜索、双击改名、真实删除、按项目过滤；
- 主列的阅读宽度稳定，Composer 只与主列对齐；
- 右栏只在有项目、资料、引用、审批或产物价值时显示；
- 手机端把历史和上下文变为 Sheet，不得挤成垂直细条。

#### Composer

- 多行输入，Enter 发送，Shift+Enter 换行；
- 附件按钮、文件预览托盘、移除、上传/解析状态；
- 上下文范围、模型、推理强度和权限采用紧凑菜单；
- 推理强度始终显示英文：`low`、`medium`、`high`、`extra`、`max`；
- 运行中发送按钮变为 Stop，用户仍可编辑下一条消息，不能整个输入框锁死；
- 不常驻显示“Sandbox: 完全访问...”说明，权限只在用户操作权限菜单时出现；
- 不允许输入区、历史栏、菜单或底部状态文本覆盖。

#### 真实执行轨迹

Agent 不是先输出一段空话再把工具卡堆在底部。每次执行必须先展示一个助手拥有的、
可折叠的 Run 轨迹：

```text
已处理 42 秒  v
  检查项目上下文                 已完成
  读取 3 份资料                  已完成
  提取 12 条要求                 运行中
  等待你批准导出                 需要确认
```

- 默认只展示用户可理解的摘要；
- 展开后显示层级：Run -> 阶段 -> 操作 -> 安全详情；
- 翻译内部工具：`search_projects` 必须显示为“搜索项目”，不出现 `tool_call_id`、JSON、
  SQL、Python trace 或原始命令；
- 当前动作使用克制 spinner 或蓝紫活动态；完成后静止；
- 支持 `Run -> Plan -> Tool -> Artifact` 的层级，支持多工具并行与部分失败；
- 长任务可后台运行，返回时恢复；取消、失败、重试、重连、确认都必须有状态；
- 最终回答在轨迹完成或明确等待审批后出现，禁止重复生成两份相同消息。

#### 审批与权限

- 必须是一个真实 HITL 组件：操作、影响对象、风险、关键参数、批准/拒绝/稍后；
- 读操作可按权限自动执行；项目创建、文件移动/删除、重新解析、导出、跨项目访问等需
  依据权限级别决策；
- 审批结果必须进入执行轨迹和审计；
- 全量权限不等于绕过删除确认或越权访问。

#### 知识与引用

- Agent 查询当前项目时，界面显示已使用“项目知识”还是“组织共享知识”；
- 引用是可点击的资料、页面、片段定位，不是孤立的 `[1]`；
- 缺证据时要明说“尚未找到可引用资料”，并给出导入/检索/人工确认下一步；
- WeKnora 检索过程只映射为产品动作，例如“在项目知识中检索”“核对共享案例”，
  不泄漏内部 RAG/向量参数。

### F. 工作流运行记录

- `运行记录` 只展示真实 `ExecutionRun` 与阶段状态；
- 运行详情以时间线/流程图结合，流程图只画真实节点和边；
- 节点状态：待处理、排队、运行、等待人工、成功、失败、取消、跳过；
- 运行中节点允许轻微呼吸/Spinner，非运行节点绝不永久发光；
- 失败节点有可操作的原因、影响范围、重试或人工修复路径；
- 可从项目、Agent Desk 与运行详情交叉跳转。

### G. 团队、模型、审计与治理

- 团队与成员：角色、项目范围、邀请、移除、最近活动；
- 模型提供商：官方预设、协议说明、模型拉取/测试、健康状态、密钥仅服务端保存；
- 审计与治理：人、Agent、系统三个 actor 类型，筛选、时间范围、对象跳转；
- 设置页按职责分组，不做无限滚动表单；
- 任何危险配置都需确认、错误恢复和可理解的空态。

## 7. 视觉系统要求

### 方向

高质量现代 B2B 工作台，接近优秀开发工具和成熟 SaaS：稳定、安静、清晰、有信息密度。

- Light：冷白/蓝灰画布、深炭文本、低对比结构线；
- Dark：石墨表面、克制层次；
- Primary：受控蓝色；Agent active/focus：低饱和蓝紫；
- Success：绿色；Attention：琥珀；Danger：红色；
- 使用 Geist Variable 或同等级可商用字体；常规 UI 字号 13-14px；
- 使用统一 token，不在局部硬编码颜色、阴影、圆角或间距；
- 数据密集区域优先表格、层级列表、分割线和留白，不用卡片海。

### 明确禁止

- 荧光绿常驻 focus、全屏渐变雾、紫色光球、赛博网格、装饰粒子；
- 彩色左描边、每个区块玻璃卡、嵌套浮卡、巨大圆角；
- 无意义滚动入场、永久呼吸、鼠标悬停三维倾斜；
- “AI 正在深度思考”之类没有事实对应的表演；
- 随机 favicon/emoji/手绘 SVG 作为品牌或提供商图标；
- 偷用竞品 logo、截图或完整布局。

## 8. 组件与交互来源规则

原型阶段需要维护 `component-inventory.md`；实现阶段必须扩展为
`COMPONENT_SOURCE_LEDGER.md`。以下能力必须有成熟来源：

| 能力 | 首选 |
| --- | --- |
| Button/Input/Menu/Dialog/Drawer/Tooltip/ScrollArea/Resizable | Base UI + 现有 shadcn 受控封装 |
| 数据加载与缓存 | TanStack Query |
| 表单验证 | Zod + 现有表单原语 |
| Toast | Sonner |
| Markdown 与数学公式 | Streamdown 或 react-markdown + KaTeX，二选一验证 |
| 代码块 | 受控 Markdown renderer |
| 流程和图谱 | `@xyflow/react`，仅真实数据驱动 |
| 轻量状态动效 | Motion，限于空间/状态变化 |
| Agent UI | 可以 POC `assistant-ui`，但不得让它拥有真实 Run/HITL 状态 |

禁止混合多个聊天库、动画库或手工重造无障碍原语。业务组合组件可以自研，但必须由以上
基础原语组合。

## 9. 响应式、无障碍与状态要求

每张关键画板至少覆盖：1440x900、1024x768、768x1024、390x844。

验收项：

- 页面无整体横向滚动；
- 所有长文件名、模型名、ID、标签可截断/换行/查看全文；
- 侧栏收起后主区域宽度真实变化；

- 图谱和流程图在移动端有列表替代视图；
- 使用色彩之外的文字/图标/形状表达成功、失败与等待。

## 10. OpenDesign 交付与评审门槛

### 第一批必须交付

1. `design-systems/bidpilot-v2/DESIGN.md` 和 token；

### 评审后才能进入 React 的条件

- 用户已逐页确认信息层级、布局、文案、色彩和交互方向；
- 没有任何文本溢出、遮挡、假数据或内部技术名；
- Agent 轨迹、审批、附件、引用和图谱有完整状态说明；
- 每个实现组件已有来源或明确的受控组合方案；
- 已标出全部 API gap，且没有以虚构接口掩盖缺口。

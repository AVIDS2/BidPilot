# 《深入理解 AI Agent：设计原理与工程实践》复读笔记与 BidPilot 对照

> 来源：李博杰，《深入理解 AI Agent：设计原理与工程实践》，v1.3，2026-07-29。  
> 输入文件：`F:/QQ下载文件/AI-Agents-in-Depth-zh-CN.pdf`。  
> 目的：把书中的工程方法映射到 BidPilot 的事实代码与产品缺口；不是产品宣传稿，也不把计划当作已实现能力。

## 0. 先给结论

书中把现代 Agent 概括为 `LLM + 上下文 + 工具`，并将生产级可靠性扩展为：

```text
Agent = LLM + [上下文 + 工具 + 约束 + 验证 + 纠正]
      = Model + Harness
```

对 BidPilot 而言，不能把“有聊天框、有 LangGraph、有很多工具”当作 Harness 已完成。当前真实情况是：

| 维度 | 事实状态 | 证据 |
| --- | --- | --- |
| ReAct 工具循环 | 已有 | `services/api/app/runtime/harness_loop.py` 将安全的工具结果作为 `ToolMessage` 回送模型。 |
| 项目业务真相 | 已有 | PostgreSQL 领域模型、运行记录、审批和交付物，不以提示词或 Agent 内存作为事实源。 |
| 运行级事件 | 已有 | `RuntimeRun`、`RuntimeEvent`、`RuntimeAction`、`RuntimeApproval` 和 SSE 事件流。 |
| 上下文分段/预算 | 已有 | `services/api/app/runtime/prompt_assembly.py`。 |
| Skills 动态装载 | 部分具备 | `build_skill_prompt_block()` 与 `select_skill_names()`；需以回归评估验证选择效果。 |
| Agent 状态栏 | 部分具备 | 每个模型回合有 `PLAN_UPDATED` 元信息，但还不是面向异步等待、唤醒、预算和下一步策略的独立状态栏产品。 |
| 用户可读 Trace | 部分具备 | UI 有运行/回合/操作标识和活动卡；此前结果被过度摘要，正在补齐受控结果与失败详情。 |
| OpenTelemetry Trace/Span | 未实现 | 当前是自定义持久化事件，不是 OpenTelemetry 的 trace/span/exporter 体系。 |
| 异步等待与唤醒 | 部分具备 | 审批、后台工作流、通知存在；审批恢复后没有稳定的“工具结果 -> 再进一轮模型决策”闭环。 |
| 评估基础设施 | 部分具备 | 有运行与测试；尚缺按任务集、轨迹、通过条件、提示词版本运行的持续离线/线上评估闭环。 |

这份笔记的后续实施原则是：**任何用户可见的“完成”必须对应一个可以验证、打开、下载、审批、重试或定位的领域事实。**

## 1. 第 1 章：Agent、ReAct 与 Harness

### 书中要点

- Agent 的观察空间来自上下文，动作空间来自工具；工具调用不是附属功能，而是与观察一起构成闭环。
- ReAct 是“观察 -> 决策/行动 -> 工具返回 -> 再观察”的多轮轨迹。工具返回缺失，下一轮模型就处于盲执行状态。
- Harness 不等于一段系统提示词。书中将上下文、工具、约束、验证、纠正合在模型外部工程中；提示工程只是其中一层。
- 编排工作流和自主 ReAct 不是互斥关系：图中的节点可以运行 Agent 循环，长期任务则需要独立持久化、验证和纠错。

### BidPilot 对照

| 书中要求 | 当前代码事实 | 差距与行动 |
| --- | --- | --- |
| 每次行动后模型获得观察 | `StreamingHarness` 将 `summary + payload` 写为 `ToolMessage`。 | 结果需保持“可行动且受控”：当前截断上限和过度摘要会丢失关键交付物身份；为导出/起草补充项目、交付物、章节身份。 |
| 约束在服务端而非只靠提示 | capability registry、审批、权限检查在服务端。 | 继续把事实校验、下载限制、幂等和失败分类放在 Adapter/Command 层，禁止靠 prompt 补安全。 |
| 验证后才宣称完成 | 导出命令检查并保存 artifact。 | 各类异步任务都要有可验证的 terminal state；不能只写“工作流完成”。 |
| 纠错有明确停止条件 | 部分工具有失败码与重试。 | 对远程下载必须保留失败原因和停止策略，禁止改 URL/协议后盲目重试。 |

### 产品命名

- **BidPilot 执行助手**：面向用户的自主 Harness Agent；负责理解目标、调用受限工具、回写结果。
- **响应工作流**：项目级、可持久化的任务编排（当前由 LangGraph/工作流节点实现）；负责资料解析、检索、计划、章节起草、审阅、人工确认、保存。
- 二者关系：执行助手可以发起、观察和解释响应工作流；响应工作流不是一个“藏在聊天里的 Agent”，而应在项目工作区中可查看、可暂停、可重试、可审批。

## 2. 第 2 章：上下文工程、提示、Skills、状态栏与压缩

### 书中要点

- 工具循环的动态轨迹由用户消息、助手行动、工具结果不断追加；静态前缀则包括系统规则和工具定义。
- 提示工程要求结构化、清晰的工具描述和抵抗提示注入；“规则堆砌”不是可替代的流程设计。
- Skill 是按需加载的领域能力单元；工具和 Skill 的职责不同，前者执行动作，后者提供选择工具和处理任务的方法。
- 状态栏应向模型提供可信的动态元信息，例如任务进度、当前时间、待办、等待状态、可用资源；它首先服务模型的轨迹管理，其次才是 UI。
- 上下文压缩应分层并保留事实、决策、未完成事项与引用；不能简单截断历史。

### BidPilot 对照

| 项目 | 事实状态 | 后续收口 |
| --- | --- | --- |
| 系统提示 | `harness_loop.py::_initial_messages()` 组装规则。 | 为每条规则建立任务型回归用例；避免继续把 UI 缺口堆成提示词规则。 |
| 上下文拼装 | `prompt_assembly.py` 分段、预算、上下文 trace。 | 给每次 prompt 装配记录版本、段落占用、截断原因；敏感内容仅用于受权诊断。 |
| 动态状态 | `PLAN_UPDATED` 写入步骤、已完成能力、失败次数、审批状态、关联工作流。 | 形成正式 status-bar schema：`objective / active_work / wait_for / wake_condition / next_check / project_facts`，由服务端生成，不信任网页文本。 |
| 压缩 | 存在会话窗口和内存召回。 | 明确压缩产物的事实来源、版本和失效策略；测试跨会话“交付物在哪里”仍能从领域读取而不是靠摘要猜。 |
| Skills | 现有按请求选择与注入。 | 对每个 Skill 定义输入、输出、退出条件和 eval case；避免把不可信外部网页写入状态栏或系统前缀。 |

### 对本次问题的直接结论

截图中“已完成”不是模型完整回答被删掉，而是 UI 将持久化 `public_summary` 压缩为泛化完成态。这个策略本意是不给用户展示私有推理或原始工具参数，但实现错误地连**交付物标题、下载路径、失败码、项目定位**也一并丢掉了。正确做法是“受控的结构化结果卡”，不是暴露 Chain of Thought。

## 3. 第 3 章：用户记忆与知识库

### 书中要点

- 记忆分层、需要治理、压缩和隐私保护；记忆不是无限追加的聊天记录。
- RAG 是文档获取管道：分块、稠密/稀疏检索、混合检索、多模态提取、结构化索引和时效管理均是质量因素。
- Agent 化 RAG 把检索变成可审计工具，模型需要能看到来源、适用范围与失败状态。

### BidPilot 对照

- 项目资料、资料包、解析资产、证据、Bid Wiki 和记忆提案都存储为领域数据；这符合“业务真相不在 prompt/runtime memory”的架构约束。
- 文档状态必须按 `parse_status/index_status` 表示。`parsed + indexed` 才可说可语义检索；`not_applicable` 是仅归档附件；其余处理中不能武断称失败。
- 当前短板不是“再做一个聊天记忆”，而是让 Agent 和 UI 在每次资料导入、解析、检索后保留**文件名、来源、资料包、处理状态、下一可执行动作**。

## 4. 第 4 章：工具与事件驱动异步 Agent

### 书中要点

- 工具要有恰当粒度、明确描述、参数保真和权限边界；阅读工具与改写工具要分开。
- 事件驱动异步 Agent 不能靠模型不断轮询。长任务应在事件到达时唤醒、继续并通知用户。
- 外部输入（网页、搜索、MCP 返回）是不可信内容；不能把其中的文本当作指令。

### BidPilot 对照

| 场景 | 当前事实 | 必须保持的设计 |
| --- | --- | --- |
| 公告研究 | `web_search` 仅发现来源。 | 搜索结果不能直接自动入库。 |
| 远程附件 | `discover_remote_documents` 只读找附件，`fetch_url_to_project(import_mode=artifact)` 才下载。 | 下载失败必须呈现稳定错误码、来源 URL、可选后续动作；不能靠“搜索、换协议、改 URL”循环。 |
| 异步工作流 | 持久化运行、事件、后台通知已存在。 | 增加 wake/re-enter 行为：审批/任务终态应带事实回到 Agent 的下一轮，而不是只显示一个通知。 |
| 用户确认 | 服务端审批持久化。 | 模型不能伪造确认卡；卡片必须对应审批 ID、执行对象、可恢复状态。 |

### 下载的工程边界

远程下载应由部署端的受控下载 Worker 执行，而不是浏览器任意代替服务器：浏览器会遇到跨域、身份、断点续传、可审计归档、私有化网络代理和对象存储一致性问题。正确的成本控制是限额、大小/类型白名单、超时、队列、缓存、对象存储和用户确认，而不是让模型把网页当文件下载。对于登录墙或用户本地可访问的站点，应提供“用户下载后上传”这一明确降级路径。

## 5. 第 5 章：Coding Agent、Harness 与可验证产物

### 书中要点

- Coding Agent 的价值不在“会生成文字”，而在于文件、命令、验证、恢复和交付物组成的可验证循环。
- 产物必须有可定位的路径或对象身份，并经检查后再交付；失败时保留足够的诊断事实。
- 代码可作为约束和适配器，把确定性规则从自然语言中移出。

### BidPilot 映射

投标交付也应采用相同标准：章节、审阅版本、导出 artifact 是可持久化的领域对象。聊天最终回答不是交付物。导出完成后，界面必须同时提供：

1. 当前交付物标题、格式、持久化状态；
2. 可点击下载；
3. 可打开项目的“交付”页；
4. 运行、回合、操作标识，供支持人员关联诊断；
5. 失败时的公开失败原因和稳定错误码。

## 6. 第 6 章：评估与可观测性

### 书中要点

- 评估需要任务环境、任务集、可验证通过条件、自动评估和人机交互测试。
- 可观测性不是仅记录最终答案：需要追踪轨迹、工具调用、耗时、失败、成本和结果；同时要有隐私边界。
- 生产级改进要依靠特性开关、消融、AB、提示词敏感性、版本化和回归，而非凭个例修改提示词。

### BidPilot 真实 Trace 分层

```text
用户会话
  -> RuntimeRun（一次执行）
     -> RuntimeEvent（计划、能力、审批、消息）
     -> RuntimeAction（工具执行）
     -> ExecutionRun（长工作流）
     -> Model usage / context-assembly trace
```

- 这已经是**领域运行记录**，支持事件关联和运维诊断。
- 这**不是** OpenTelemetry Trace/Span：目前没有标准 OTel span、trace exporter、跨服务 trace propagation 或专门的遥测后端。
- 用户 UI 不应展示私有推理链、原始提示词、私密凭据或完整工具参数。应展示的是公开摘要、受控事实、错误码、来源、耗时和跳转/下载操作。

### 评估缺口与验收集

后续必须维护如下最小回归任务集，并作为 CI/发布门禁的一部分：

| 任务 | 通过条件 |
| --- | --- |
| 创建项目 -> 上传资料 -> 解析 | 项目/文档/资料包持久化；状态与 UI 一致。 |
| 发现远程附件 -> 用户确认 -> 下载入库 | 仅附件进入资料包；失败有原因且无重复盲重试。 |
| 资料检索 -> 起草 -> 审阅 -> 导出 | 每一步产生可读领域对象；导出可点击下载且可在项目页复查。 |
| 审批暂停/恢复 | 无重复写入；恢复后 Agent 获得真实结果并继续或说明等待。 |
| 问“文件在哪里” | Agent 调用领域读取工具；不虚构本地路径。 |
| Provider/网络失败 | 有关联运行 ID、公开错误、重试策略和用户可选动作。 |
| 跨会话追问 | 从项目/交付物读模型恢复事实，而不是信任旧消息摘要。 |

## 7. 第 7 章：模型后训练

书中区分预训练、SFT、RL、数据和环境，并强调多轮任务中的过程与结果信号。对 BidPilot 的含义不是立即训练模型：先把高质量、可验证的真实任务轨迹做成评估数据；只有当 prompt/harness/tool 修正无法满足指标时，再讨论 SFT 或偏好数据。任何“训练优化”都不能替代项目权限、审批和领域事实校验。

## 8. 第 8 章：持续进化

书中提出从轨迹获取学习信号，将经验沉淀为知识、指令、程序或参数，并要求验证、发布与回滚。BidPilot 的落点：

- 将已验证的失败模式写为测试、Adapter 校验、领域规则或受审核的项目知识，而不是无审计地追加 prompt；
- 对 prompt、skill、工具 schema、模型配置做版本化；
- 以任务集得分、失败率、人工纠正率和交付物可下载率决定发布；
- 永远保留回滚路径，不从用户生产对话中自动学习并直接改写系统行为。

## 9. 第 9 章：多模态与实时交互

本项目当前与本章最直接相关的是文档/OCR/附件处理与流式文本，不应将语音、Computer Use 或机器人能力包装成已经支持。文档预览、下载、解析状态和表格/图像抽取应以真实 parser/OCR 状态为准；用户可见的流式输出应来自模型可见文本或公开进度事件，不能把内部推理伪装成答案。

## 10. 第 10 章：多 Agent 协作

书中强调是否共享上下文、协作拓扑、并发冲突和错误级联。BidPilot 的“响应工作流”目前更适合作为**受领域数据约束的阶段编排**，而非把每个节点吹成独立人格 Agent：

- Supervisor 决定下一节点；
- 解析、检索、计划、起草、审阅、人工确认、保存共享项目事实但遵从权限和版本边界；
- 章节并发必须防止版本冲突；
- 一处错误必须标记局部失败、允许人工介入或重试，不能被下游步骤放大成“全部完成”。

## 11. 本次 UI 与运行时改动的验收映射

本次变更针对的不是视觉换皮，而是上述第 1、2、4、5、6 章的可验证闭环：

| 症状 | 变更 | 验收 |
| --- | --- | --- |
| “XXX 已完成” | 用服务端公开 summary 与受控事实卡替换前端泛化文案。 | 成功卡显示交付物/文件/资料包/状态等真实字段。 |
| 失败不清楚 | 展示安全错误信息和稳定 error code。 | 用户和支持人员能区分远程下载拒绝、参数错误、模型/provider 错误。 |
| 文档找不到 | 导出结果保留 `project_id/deliverable_id/title/download_path`。 | 能点击下载或打开项目“交付”页。 |
| 看不到画布 | 工作流结果保留项目与章节身份，并提供“查看任务编排”。 | 打开 `/projects/:id?surface=workflow`。 |
| 空会话过于靠上 | 仅调整无消息欢迎区的垂直留白。 | 有消息会话的滚动/输入区不受影响。 |
| Agent 猜成果位置 | prompt 规定追问交付物位置时先读取真实领域状态。 | 回归测试验证不以聊天话术作为事实源。 |

## 12. 尚未完成、不得误报的事项

1. 将自定义运行事件映射到完整 OpenTelemetry trace/span，并接入可查询的 exporter/后端。
2. 审批与后台任务终态后的统一唤醒：把“真实工具结果”送入下一次模型回合或显式生成下一步状态，而不是只结束通知。
3. 用户级运行详情页：按项目、会话、运行、执行节点检索并查看公开 span/事件、成本、耗时与重试。
4. 正式的 Agent Status Bar schema 与可视化，而非仅用 `PLAN_UPDATED` 事件临时承载状态。
5. 任务集、裁判、提示版本和线上指标构成的持续评估系统。

这些是后续 P0/P1 工程工作，不能因为聊天页面已经能显示某些运行信息就宣布完成。

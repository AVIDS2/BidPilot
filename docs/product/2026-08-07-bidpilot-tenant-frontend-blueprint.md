# BidPilot 租户产品侧前端蓝图

> 状态：产品重构基线
>
> 范围：客户租户的管理台与投标工作台。BidPilot 内部运营后台不在本轮
> 范围内。`/agent` 的现有交互不在本文件对应的页面改造范围内。

## 1. 定位与边界

BidPilot 是面向企业投标响应团队的 SaaS，不是给开发者观察 Agent
运行日志的控制台，也不是由 Agent 替代人完成全部工作的黑盒。

产品要同时服务两类租户内用户：

1. **投标工作者**：负责机会评估、材料整理、需求合规、章节写作、审阅和
   交付。他们需要直接看见并操作业务对象。
2. **租户管理员**：负责组织、成员、权限、模板、集成、用量和安全。他们
   需要管理本公司使用 BidPilot 的方式，而不是维护 BidPilot 平台本身。

Agent 是贯穿两类场景的自然语言操作入口：它可以创建、查询、建议、启动
受控工作流，且每一项成果必须落到可由人继续处理的业务对象和页面。它不是
产品导航中心，也不应把 trace、run、token 或工具调用当成用户的日常工作。

业务闭环是：

```text
机会识别 -> 立项与决策 -> 资料入库与解析 -> 要求与证据 -> 响应计划
-> 章节协作 -> 审阅定稿 -> 交付与复盘 -> 组织知识复用
```

每一段都必须既能由用户页面操作，也能由 Agent 发起后跳转至对应对象。

## 2. 三端边界

| 产品面 | 服务对象 | 目的 | 是否本轮实现设计 |
| --- | --- | --- | --- |
| 租户投标工作台 | 投标经理、方案、技术、审阅者 | 完成一项真实投标响应 | 是 |
| 租户管理台 | 企业管理员、采购/IT 管理员 | 管理本企业的成员、权限、配置与订阅 | 是 |
| BidPilot 内部运营后台 | BidPilot 运维、支持、研发 | 支持租户、排障、全局运维、计费异常 | 否，后续独立设计 |

绝不能把内部运营页混入客户侧导航，更不能把客户侧的“运行记录”做成日常
一级菜单。租户可见的诊断只出现在相关业务对象的失败状态、恢复入口和审计
详情中。

### 2.1 账户与工作区：多租户是架构，不是注册门槛

BidPilot 的数据、权限、账单和文件必须有组织边界，因此底层必须多租户；但
“先创建租户，才能注册”是错误的用户体验。对用户可见的名称应是**工作区**或
**团队空间**，而不是技术词“租户”。

推荐的开户路径：

```text
邮箱/SSO 注册
  -> 自动创建“我的 BidPilot 工作区”，该用户为所有者
  -> 可立即体验雷达、建机会、导入资料、创建单人项目
  -> 需要协作时：创建企业工作区或接受团队邀请
  -> 加入后：在组织切换器中进入企业工作区，项目与资料自动隔离
```

邀请链接优先进入目标企业工作区；企业 SSO/SCIM 场景由管理员预配置成员并禁止
个人工作区外流。一个用户可属于多个工作区，但每次业务操作都带有明确的
`organization_id`，项目、文档、知识资产、账单和审计记录均不可跨工作区读取。

这也区分了两类产品：

| 场景 | BidPilot 的体验 |
| --- | --- |
| 个人/小团队试用 | 普通注册、自动个人工作区、之后邀请同事 |
| 企业投标协作 | 管理员建立或认领企业工作区，成员以角色加入 |
| 外部顾问/评审 | 受限邀请到指定工作区或项目，不暴露其他资料 |
| 官方电子交易与正式递交 | 跳转/对接外部交易平台的企业认证、CA、电子签章等法定流程；这不是 BidPilot 自己的注册门槛 |

国际响应管理 SaaS 通常采用“账号 + 工作区成员”的协作模型；国内电子招投标
交易平台则因资格、签章和法定递交要求更强调企业认证。BidPilot 是前者的工作
平台，可为后者准备并导出材料，但不能把官方交易平台的准入流程复制成自身的
初始注册流程。

## 3. 导航与整体框架

### 3.1 全局骨架

- 统一使用已有的 **252px 可伸缩侧栏** 与 **46px 全局工具栏**；每条路由
  不得自行重建壳层。
- 侧栏只保留稳定、可理解的工作入口：`首页`、`招采雷达`、`我的工作`、
  `投标机会`、`知识库`、`Agent`。
- 租户管理收纳在工作区/账户菜单的“组织设置”，不和日常投标操作混排。
- 通知使用右上角 Sheet/Popover 处理，点击后跳到对应项目、审阅或任务；不做
  一个按系统事件无限堆叠的“收件箱”。
- `/agent` 保留为 Agent 的专属会话表面。其他页面通过“询问 Agent”带入当前
  项目、文档、章节或要求上下文，不自动打断用户正在进行的页面操作。

### 3.2 页面共同结构

```text
全局工具栏：组织切换 | 全局搜索 | 新建 | 通知 | 账户
侧栏：主工作入口
页面主体：固定页头（标题、范围、主动作）
          可选本地横向标签栏
          局部滚动的业务内容
          上下文侧检视器（按需打开，不常驻占宽）
```

不采用“左边项目列表 + 右边只读详情”的通用模板。项目选择应来自项目页、
全局切换器或当前项目头部；详情页面应让主体区域承担实际操作。

### 3.3 信息与视觉规则

- 一个页面只围绕一个主要决策或工作对象组织。标题、当前范围和主动作必须在
  首屏明确出现。
- 用留白、对齐、字号层级和少量锚点分隔组织信息，不给每一行都画上下边框。
- 卡片只用于需要边界的比较、图表、检查器和临时浮层；普通清单、表格和编辑
  区使用安静行与局部滚动。
- 每个操作状态都能继续做事：空态给创建/导入动作，阻塞态给负责人或所缺资料，
  失败态给可理解的原因和重试/恢复；不展示无法行动的“日志花瓶”。
- 图表只回答正在影响决策的问题，例如截止风险、覆盖率、审阅积压、交付就绪度。
  所有数值来自真实记录；没有数据时显示下一步，而不是伪造图线。
- 交互使用 shadcn/ui 的现有组件和语义 token。控制、菜单、Sheet、Popover、
  Tabs、Table、ScrollArea 的展开/收起统一使用 120-180ms 的 opacity、transform
  和 grid-size 过渡，焦点、空白处关闭、Esc、点击外部关闭均按组件原生行为处理。

## 4. 租户投标工作台

### 4.1 首页：今天该推进什么

**用户问题**：今天应该先处理哪一个风险、审批或截止项？

**页面内容与动作**：

- 顶部显示当前组织与日期范围；主动作是“新建机会”与“导入招标资料”。
- “需要我处理”是可领取/完成/转交的任务与审阅，不是通知文本复制品。
- “临近节点”按截止时间展示机会、交付和审批；用户可改负责人或日期。
- “投标健康”显示真实的材料解析、要求覆盖、审阅阻塞和交付就绪趋势，并能
  钻取到某个项目的对应标签页。
- “最近协作”只显示与本人相关的评论、版本、指派和决定，点击进入对象。

**不用放的内容**：Agent 工具日志、所有历史运行、开发错误、空的总指标卡。

**后端落点**：`notifications`、`collaboration`、`changes`、`readiness`、
`projects`、`review`。当前缺少跨项目“我的待办”聚合接口和仪表盘聚合接口，
应先补 API 再写假数据 UI。

### 4.2 招采雷达：从公开信号到可评估机会

**它不是什么**：不是新闻刊物、行业媒体首页或无限下拉的信息流。用户不需要
“看更多招标新闻”，而需要更早发现与自身能力相关、且仍来得及行动的招采信号。

**它解决的问题**：企业在正式招标公告之前就可能看到采购意向、征询、资格预审、
预算动态或客户采购线索；正式公告发布后又需要迅速判断资格、截止时间、地域和
投入产出。雷达负责发现、订阅、判断和转化，不替用户替代 Go/No-Go 决策。

**来源策略**：首先接入可核验的公开来源，例如中国政府采购网的政府采购信息
公开入口，以及中国招标投标公共服务平台的招标公告入口；后续才允许经授权的
行业数据库、企业信息源或客户 CRM。每条结果必须保留来源、原始链接、抓取时间、
公告时间、有效性状态和引用快照，不能把模型摘要当成公告原文。

**布局**：

```text
固定页头：招采雷达 | 保存的订阅 | 新建订阅
本地标签：为我推荐 | 全部公告 | 采购意向 | 招标公告 | 已保存 | 已忽略
筛选条：行业 | 地域 | 预算区间 | 截止日期 | 来源 | 资格/关键词
主体：按“可行动性”排序的机会流（紧凑行，不是新闻卡片墙）
右侧 Sheet：公告原文摘要、关键字段、匹配理由、原始来源、相似历史项目、动作
```

**每条信号至少显示**：采购方、公告类型、发布日期/截止日、地域、预算或项目
规模（若来源给出）、来源、匹配标签和时效状态。右侧详情允许用户：保存、忽略、
设提醒、指派同事、反馈“不相关”、新建立项、合并到已有机会、打开原始公告。

**趋势热点不是装饰性图表**。页头可放三个真实、可点击的短周期信号：关注行业
的公告量变化、未来 14 天截止密度、被保存机会的地域/采购方聚集；点击必须落到
对应筛选结果。没有订阅或来源数据时，显示“创建首个订阅”，而不是空折线图。

**Agent 的角色**：可由用户要求“找本周华东数据平台类机会”“解释这一公告的
资格要求”“把已保存公告转换为立项草案”。Agent 只能建议筛选/摘要/建档，立项
和 Go/No-Go 仍由人在机会页确认。

**新增领域与接口**：现有 `opportunities` 只覆盖已创建项目的评估与决策，不能
承担外部发现。需要新增 `notice_sources`、`notice_subscriptions`、`notice_items`、
`notice_matches`、`saved_opportunities`，以及来源连接器、去重、快照、订阅任务和
“转为项目/合并项目”的审计化 API。数据采集应作为受限扩展/连接器运行，不能由
聊天页面临时爬取来充当产品能力。

### 4.3 我的工作：个人执行队列

**用户问题**：哪些事项等我决定、撰写、补证据或确认？

**布局**：固定页头 + `待我处理 | 我负责 | 已完成` 横向标签；主体为可筛选的
任务表，不再有左侧项目二次列表。

**可操作项**：接受/转交、设置优先级和截止日、打开关联章节/要求、提交审阅
决定、标记完成。每一行都有项目、对象、状态、负责人、截止日和下一步，而不是
只有“进行中”。

**后端落点**：`collaboration`、`review`、`requirements`、`response_plans`。
缺少统一任务实体时，先定义 Task/Assignment 领域模型，不能用通知记录冒充任务。

### 4.4 投标机会：组合与立项

**用户问题**：我们有哪些机会，值不值得投，下一步由谁负责？

**布局**：页头含“新建机会/导入 RFP”；`全部 | 待决策 | 进行中 | 已归档` 标签；
筛选条；按截止时间和健康状态排序的机会表。右侧详情仅在点击行后以 Sheet 打开，
不占常驻空间。

**每个机会行显示**：客户/采购方、截止日、负责人、阶段、Go/No-Go、材料状态、
准备度、最近活动。用户可创建、编辑、归档、指定团队、记录决策、直接进入项目。

**机会详情 Sheet**：基本信息、资格判断、竞争/风险、决策记录、关键附件、下一步。

**后端落点**：`projects`、`opportunities` 的 assessment/decision、`documents`、
`readiness`。需要在 ProjectRead 中补充排序和列表需要的截止日、负责人、阶段等
聚合字段，避免前端 N+1 拼装。

### 4.5 项目工作区：一项投标的真实生产空间

项目页路由保持 `/projects/:id`，固定项目头部包含：项目名、阶段、截止日、
健康状态、成员入口、主动作和“询问 Agent”。在同一头部下使用本地标签：

```text
概览 | 资料 | 要求与合规 | 响应计划 | 章节 | 审阅 | 交付
```

#### 概览

- 只展示会改变今天决策的内容：截止节点、当前负责人、阻塞风险、准备度、未解决
  要求、待审章节、最近决定。
- 可执行“推进下一步”“指派负责人”“调整里程碑”“启动资料检查”。
- 不做将全项目所有字段塞进卡片的摘要墙。

#### 资料

- 主动作：上传、从知识库添加、导入链接。上传后进入服务端对象存储和解析队列，
  返回解析/OCR/索引状态；失败可查看原因、重试或替换文件。
- 主体是资料表：名称、类型、来源、解析状态、语言、更新时间、使用位置。
- 点击资料以右侧可拖拽宽度的 Sheet/检视器预览。PDF/图像预览，DOCX/表格转换
  预览和元数据，解析文本与页码/段落定位在同一检查器中。它是通用资产画布，不是
  PDF 专用面板，后续可承载报告、图表、HTML 预览和 Agent 产物。
- 资料可分类、去重、加入资料包、重新解析、查看被哪些要求/章节引用。

**后端落点**：`documents`、`bundles`、`parsed_assets`、`evidence`、`retrieval`。
上传与 OCR/解析不应靠聊天暂存附件；聊天附件应先成为持久化文件对象，再由会话
引用其 ID。

#### 要求与合规

- 主体是需求矩阵：要求原文/来源、类别、优先级、负责人、证据、关联章节、
  当前判定和审批状态。
- 支持批量指派、添加证据、建立/审批决定、创建/核验主张、过滤“无证据”“即将
  逾期”“需决策”。
- 单行打开要求检视器，展示原文上下文、证据链、讨论和变更历史。

**后端落点**：`requirements`、`evidence`、`readiness`、`review`。

#### 响应计划

- 以阶段和章节责任为核心，展示里程碑、依赖、负责人、资料缺口和下一步。
- 用户可改计划、重新排期、分配负责人、批准计划、启动或恢复受控起草。
- 运行中的工作流只在相应计划/章节下显示状态与“继续/取消/查看详情”，不会在
  导航中单独变成 “Runs” 产品页。

**后端落点**：`response_plans`、`drafting`、`execution`、`collaboration`。

#### 章节

- 左侧为轻量章节树，中间为 TipTap 编辑/版本对比区，右侧按需打开“证据/评论/
  历史”检视器。三栏是编辑器特例，不能泛化到其他所有页面。
- 支持手动写作、引用证据、请求 Agent 草拟、比较版本、恢复 checkpoint、提交审阅。
- 每段 AI 生成内容必须可显示证据来源、版本和人类修改，且用户能脱离 Agent 编辑。

**后端落点**：`drafting`、`versions`、`evidence`、`review`、`changes`。

#### 审阅

- 默认显示项目审阅队列而非章节目录。按“待我决策/需返工/已通过”筛选。
- 每条审阅显示影响章节、变更摘要、讨论、证据状态、负责人和截止日期。
- 支持批准、要求修改、评论、指派二审；决定必须写入结构化审阅记录。

**后端落点**：`review`、`changes`、`collaboration`、`versions`。

#### 交付

- 展示交付物组成、章节完整性、预检、格式、最后版本与收件方/提交节点。
- 用户可新建交付物、调整章节顺序、运行预检、导出 DOCX/PDF、下载历史版本。
- 如果导出被后台工作占用，显示明确的占用对象和可恢复动作，不重试到无穷。

**后端落点**：`deliverables`、`export`、`readiness`、`versions`。

### 4.6 知识库：可复用、可治理的组织资产

**用户问题**：哪些经过验证的内容、资料和经验可用于下一个标？

**布局**：页头“新增资产/导入资料”；`内容片段 | 资料来源 | 已归档` 标签；可按行业、
能力、状态、来源、最近使用筛选的表格或紧凑列表。点击进入可编辑详情页/Sheet。

**可操作项**：创建内容资产、提交新版本、发布、归档、查看来源和被哪些项目使用、
应用到项目。仅展示来源明确的资产，不把模型临时记忆当作可复用事实。

**后端落点**：`content_library`、`memory`、`retrieval`、`documents`。

## 5. 租户管理台

租户管理是企业管理员的设置中心，不是只有“模型提供商”一页。统一路由前缀可
采用 `/organization`，使用固定页头与本地横向标签：

```text
组织资料 | 成员与团队 | 角色与权限 | 模板与品牌 | 集成 | 用量与订阅 | 安全与审计
```

| 标签 | 实际工作 | 已有后端基础 | 必要缺口 |
| --- | --- | --- | --- |
| 组织资料 | 名称、默认语言、工作区策略 | `organizations` | 品牌与默认工作流配置 |
| 成员与团队 | 邀请、移除、团队归属、项目成员 | `organizations`、`teams`、`invitations`、`projects` | 角色说明与批量管理 |
| 角色与权限 | 分配/审查项目与组织权限 | `organizations`、`access` | 可视化角色策略与权限矩阵 |
| 模板与品牌 | 响应模板、术语、交付外观 | `scenarios`、内容资产 | 正式模板与品牌领域模型 |
| 集成 | AI 提供商、Skills/MCP、资料来源 | `providers`、`runtime` | 秘密托管状态、连接权限、健康摘要 |
| 用量与订阅 | 套餐、预算、额度、账单负责人 | `usage`、`billing`、`organizations` | 趋势聚合与预警规则 |
| 安全与审计 | 成员变化、敏感导出、授权操作 | `audit` | 面向租户的可筛选审计读模型 |

每个标签只显示管理员可改变的设置和结果；平台级密钥、全局任务、其他租户数据
永远不可见。

## 6. Agent 的位置与交接规则

1. 用户在任何业务对象中可点“询问 Agent”，上下文显式传入：当前组织、项目、
   文档、章节、要求或交付物 ID。
2. Agent 启动或修改业务动作后，返回对象链接和状态。例如“已提取 42 条要求，
   其中 6 条待分配”，链接到项目的“要求与合规”标签，而不是让用户阅读工具日志。
3. Trace 只留在会话内：默认收起为简短的可读工作说明；工具、来源、文件改动和
   可恢复错误按需展开。它从持久化事件树回放，但不成为侧栏的常规页面。
4. 长任务继续运行时，项目的计划、章节或交付标签显示真实状态。用户可以从业务
   页面暂停、恢复、查看失败理由；无需回到聊天才能接管。
5. Agent 不得自动跳转用户页面。只有用户点击结果链接、明确请求打开对象，或
   主动选择“在页面中查看”时才导航。

本项目已经有 shadcn/ui 的 `Sidebar`、`Tabs`、`Table`、`ScrollArea`、`Sheet`、
`Dialog`、`DropdownMenu`、`Field`、`Select`、`Tooltip`、`Chart`、`Empty`、
`Skeleton`、`Sonner`、`AlertDialog` 等组件。后续页面首先组合这些组件：

| 需求 | 首选组件 |
| --- | --- |
| 稳定导航、项目范围 | Sidebar、Breadcrumb、DropdownMenu |
| 页面模式切换 | Tabs、ToggleGroup |

## 8. 数据与状态准则

### 8.1 业务真相

- 业务对象、权限、审阅决定、解析状态、交付版本和 Agent 事件树写入服务端
  真实数据存储；浏览器只保存短期 UI 偏好。
- 文件上传后先持久化到对象存储并产生 `document/parsed_asset`，OCR/解析异步
  进行。会话只保存附件引用；刷新和切换不应丢失附件、预览或解析状态。
- Supabase 可承担 Auth、Postgres/pgvector、Storage、Realtime、备份等通用能力；
  FastAPI 保持业务控制面，LangGraph 只负责执行编排。服务角色密钥只在服务端
  使用，不能进入浏览器。

### 8.2 每个可操作对象的状态

| 状态 | 页面必须展示 | 用户可做什么 |
| --- | --- | --- |
| 未开始/为空 | 缺少什么与首个动作 | 创建、导入、指派 |
| 处理中 | 对象、阶段、可见进度 | 离开后继续、取消或稍后查看 |
| 等待人工 | 缺少的决策/字段/负责人 | 选择、批准、补充、转交 |
| 失败 | 可理解原因、影响范围 | 重试、恢复、替换输入、联系支持 |
| 已完成 | 结果与下游入口 | 查看、继续审阅、导出、复用 |

不显示孤立的“运行中”“已完成”“失败”文字堆叠；状态必须依附于可识别的项目、
文件、章节、要求或交付物。

### 8.3 Agent 记忆：默认有用、范围可控、随时可忘

《AI Agents in Depth》第三章区分了会话轨迹、跨会话长期记忆和业务状态。这个
区分适用于 BidPilot：历史聊天不是长期记忆，项目资料也不是个人偏好；三者
必须分别存储、检索和授权。

| 层次 | 保存内容 | 生命周期与访问边界 | Agent 如何使用 |
| --- | --- | --- | --- |
| 当前会话/任务记忆 | 当前消息、附件引用、已完成工具结果、未完成计划、结构化会话摘要 | 该会话与其持久化事件树；按时间追加，不能被前端刷新丢失 | 维持多轮对话和恢复正在做的事 |
| 当前项目业务上下文 | 项目、文档、要求、计划、章节、审阅、交付物 | 只在当前组织且已授权项目内；业务表是真相 | 根据当前页面/任务按需检索，不复制进个人记忆 |
| 用户长期记忆 | 写作风格、默认偏好、常用行业/区域、确认过的工作习惯、用户授权的历史摘要 | 绑定 user + organization；跨会话可用，跨组织隔离 | 与当前目标相关时选择性召回，帮助减少重复沟通 |
| 项目共享记忆 | 已确认的项目事实、决定、术语、经验总结 | 绑定 project + organization；项目成员可见 | 在该项目后续会话、计划和起草中引用 |
| 组织共享知识 | 已审核、发布且可复用的模板、术语、案例、流程 | 绑定 organization；按角色及发布状态读取 | 作为知识库来源，不以“私人记忆”名义注入 |

**全局记忆开关**：在“账户设置 > 个性化与记忆”提供“让 Agent 记住我的工作
偏好”开关，默认开启。开启后，Agent 可以从完成的会话中提炼低风险、稳定的
个人偏好，并在后续相关任务中调用；关闭后不新增、不召回用户长期记忆，当前
会话和当前项目的必要上下文仍正常工作。关闭不会删除既有记忆，用户可选择
“清除全部个人记忆”。

**用户控制面**：设置页显示每条记忆的内容、来源会话/项目、作用域、更新时间、
到期时间和最近使用。用户可编辑、删除、逐条“不要再记住”、或在任意 Agent
答复中执行“忘记这条”。不提供一个黑箱的“Agent 知道一切”开关。

**写入策略**：

1. 会话结束或明确动作后，后台从小范围上下文提取候选记忆，而不是把整段聊天
   原文写入长期库。
2. 与已有记忆检索比对后，结果只能是新增、更新、失效/删除或不操作，避免
   重复和互相矛盾的偏好长期累积。
3. 低风险个人偏好可自动保存并告知用户；项目事实、招标资格、报价、客户信息、
   外部指令和共享知识必须带来源与审批，不能因模型猜测自动成为长期事实。
4. 每次召回必须先做组织、项目、成员角色和来源可用性过滤，再按当前任务的
   相关性、时效性和置信度取少量结果。长期记忆是检索对象，不是被全量塞进提示词。

**已有基础与缺口**：当前后端已有 `user_private`、`project_shared` 作用域，
记忆上下文查询、编译、图谱提案、审批和证据映射能力。P0 需要将其接到 Agent
的读取/候选写入流程和用户设置控制面；P1 再增加组织级已发布知识的正式作用域、
冲突/到期策略、检索审计和一键清除导出。任何记忆都不得绕过项目访问控制。

## 10. 分阶段实施

### P0：先让每个页面有真实工作

1. 统一壳层、全局导航、局部滚动和页面头部，移除路由私有壳层。
2. 建立“招采雷达”最小闭环：一个官方来源、订阅、公告快照、保存与手动转化立项。
3. 将 `/projects` 改为机会页，将 `/projects/:id` 改为带本地标签的项目工作区。
4. 优先完成“资料”“要求与合规”“响应计划”“章节”“审阅”“交付”的可操作
   页面，直接接已有 API。
5. 把 `/runs`、开发式 Inbox 从客户一级导航撤出；在相关对象失败时提供恢复入口。
6. 将附件改为持久化 document 引用和统一预览画布，不再依赖聊天暂存。

### P1：补齐个人与组织协作

1. 新建可分配任务/待办聚合接口，完成“我的工作”和首页行动面板。
2. 完成知识资产的发布、归档、使用追踪。
3. 完成组织设置中心的成员团队、权限、模板、集成、用量和审计标签。
4. 为机会、准备度、审阅和交付提供真实聚合指标与钻取。

### P2：提升而不喧宾夺主

1. 基于实时状态做截止风险、合规覆盖和审阅吞吐图表。
2. 将 Agent 的业务结果变成各页面可订阅的建议/草稿/行动，而非独立日志。
3. 设计单独的 BidPilot 内部运营后台，使用独立 RBAC、域名/路由和数据视图。

## 11. 验收标准

- 投标经理无需打开 Agent，即可从机会创建到完成一次资料入库、要求分派、章节
  审阅和交付导出。
- Agent 创建/变更的任何项目成果都能一键进入对应业务对象，且页面刷新后仍存在。
- 用户侧导航中没有“运行日志/工具调用”类一级入口；错误信息均有明确业务上下文
  和可恢复动作。
- 每个高频页在桌面和窄屏下具有固定页头、局部滚动、无横向溢出和稳定密度。
- UI 优先采用现有 shadcn/ui 组件，使用统一 token、字体和交互时序；不引入新的
  手搓视觉语言。
- 运营后台与租户管理/投标工作台在权限、导航和数据范围上物理分离。

## 12. 面向真实生产的投标闭环

前述页面信息架构不是产品完成定义。一个企业可以把 BidPilot 用于真实生产，
必须完成下面的端到端闭环；任一步只显示数据而不能操作，都不能算交付。

| 阶段 | 人的工作与决策 | 平台必须产出 | Agent 可以做什么 | 缺少时的风险 |
| --- | --- | --- | --- | --- |
| 1. 发现 | 订阅、筛选、保存潜在线索 | 有来源和时效的公告/线索记录 | 摘要、匹配、提醒、去重 | 用户找不到可投项目 |
| 2. 立项 | Go/No-Go、负责人、截止日、投入判断 | 可审计的机会决策与项目档案 | 提取关键资格/期限，提出风险 | 项目没有明确所有者和边界 |
| 3. 入库 | 上传 RFP、附件、历史材料，修正分类 | 原文件、解析文本、OCR、页码、解析状态 | 识别文件类型、提示缺页/重复 | 回答无法追溯，资料刷新即丢失 |
| 4. 合规 | 确认要求、分配责任、补齐证据 | 要求矩阵、证据链、责任人和截止日 | 提取要求、建立章节/证据映射 | 漏掉硬性资格或废标项 |
| 5. 计划 | 批准章节、里程碑、协作分工 | 响应计划、依赖、任务与可恢复工作流 | 提议拆解、更新风险、起草受控任务 | 起草变成无序聊天 |
| 6. 创作 | 写作、引用、修订、版本选择 | 可编辑章节、版本、引用、变更记录 | 基于受控证据起草、重写、核验 | 生成内容不可控或无法解释 |
| 7. 审阅 | 方案/法务/商务审阅与签核 | 审阅队列、评论、决定、返工闭环 | 汇总变更、提示未解决问题 | 无人对最终内容负责 |
| 8. 交付 | 预检、生成文件、正式递交、留存回执 | 交付包、DOCX/PDF、检查清单、提交记录 | 准备交付、运行检查、生成递交说明 | 导出的文件不可用或无法追责 |
| 9. 复盘 | 记录中标/失标、经验和可复用内容 | 结果、复盘、已发布知识资产 | 总结差距、建议沉淀资产 | 每次投标从零开始 |

### 12.1 P0 可生产的最小闭环

P0 不追求覆盖全国所有交易平台，也不把所有行业情报都接进来。它必须让一个
3-10 人的响应团队在一个工作区内完成一次真实内部投标生产：

```text
导入或手动建立机会
-> Go/No-Go 与负责人
-> 上传 RFP 和全部附件
-> 服务端解析/OCR 并确认资料完整
-> 生成并修订要求矩阵
-> 分派章节与截止节点
-> 人工/Agent 协作起草且带证据
-> 审阅决定与版本冻结
-> 预检、导出、登记递交回执
-> 写入结果与可复用知识
```

这里的“递交”初期可以是用户下载 BidPilot 生成的合规文件后，在官方交易平台
人工递交；BidPilot 记录递交时间、收件系统、文件版本和回执附件。只有当某个
交易平台有合法、稳定且获授权的接口时，才把自动递交做成独立连接器。

### 12.2 当前必须补齐的业务能力

以下不是可有可无的“以后加几个页面”，而是 P0 或 P1 的真实生产前置条件：

| 能力 | 优先级 | 需要的领域/API | 用户表面 |
| --- | --- | --- | --- |
| 机会字段与 Go/No-Go 决策 | P0 | 项目扩展、`opportunities` 决策历史 | 机会页与项目概览 |
| 截止节点、任务、指派、提醒 | P0 | `Task`/`Assignment`、日历与聚合查询 | 我的工作、计划、首页 |
| 异步解析/OCR 状态与页级定位 | P0 | `documents`、`parsed_assets`、worker 诊断 | 资料页与预览画布 |
| 可审核的要求矩阵与证据覆盖 | P0 | 现有 `requirements`/`evidence` 的聚合读模型 | 要求与合规 |
| 编辑、版本冻结、审批与返工 | P0 | `drafting`、`versions`、`review`、`changes` | 章节与审阅 |
| 预检、交付版本、递交回执 | P0 | `deliverables`、`export`、SubmissionRecord | 交付 |
| 结果与复盘、知识发布 | P1 | Result/Retrospective、`content_library` | 项目概览、知识库 |
| 公开公告订阅与转化 | P1 | Radar 领域与来源连接器 | 招采雷达 |
| 企业 SSO/SCIM、精细 RBAC | P1 | `auth`、`organizations`、`access` | 组织设置 |
| 自动递交到第三方平台 | P2 | 平台专属授权连接器 | 交付，不作为通用承诺 |

### 12.3 生产可靠性底线

- 资料、任务、要求、审阅决定、版本、导出和提交回执必须持久化；刷新、切换
  会话和重新登录不能改变业务真相。
- 解析、检索、起草、导出等长任务需要幂等键、状态机、取消/恢复和明确失败原因；
  不依赖浏览器保持连接，也不通过反复重试掩盖失败。
- 每一段 AI 内容、要求判定和交付版本都要能追溯到用户、时间、来源和版本。
- 团队成员只能看到其工作区和被授予的项目；导出、权限变更、成员移除和敏感
  资料访问需要租户审计记录。
- 用户可不使用 Agent 完成全部关键路径；Agent 失效不能阻断项目、资料、编辑、
  审阅和导出。

### 12.4 当前设计的诚实结论

目前已经有不少后端领域基础与 Agent 运行时，但它还不是可直接承诺生产使用的
完整产品：跨项目任务聚合、公告雷达、提交回执、复盘结果、品牌/模板、租户级
权限读模型和端到端质量门尚未完整落地。下一阶段应先实施上表的 P0 闭环，再做
宽泛的数据面板、自动提交和内部运营后台。
